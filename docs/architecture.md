# ReMinix — архитектура системы

> Документ описывает архитектуру кодовой базы **ReMinix** — форка MINIX 3, взятого за
> основу для портирования на amd64, arm32, aarch64, risc-v64 и mips64 и развития как
> микроядерной ОС для встраиваемых систем.
>
> Составлено при первичном изучении кодовой базы (сентябрь 2026). Обновляйте этот файл,
> когда меняется сама архитектура, а не детали реализации — для текущего состояния работы
> смотрите `docs/handoff.md`.

## 1. Что такое ReMinix

ReMinix — независимый form MINIX 3 (последняя версия ветки `master`, синхронизированная
с NetBSD-8). Оригинальный MINIX 3 разрабатывался как учебная и исследовательская
микроядерная ОС группой Andrew S. Tanenbaum (Vrije Universiteit Amsterdam); начиная с
MINIX 3.2 проект активно заимствовал userland и часть исходников ядра NetBSD (см. `sys/`,
`external/`, `gnu/`, `tools/`), сохранив микроядерную архитектуру.

Согласно `README.MD`, права на оригинальный код принадлежат A. Tanenbaum (BSD-3-Clause),
новые изменения — Denis Mironov (2026), лицензия всего дерева — BSD-3-Clause, если не
указано иное в конкретных поддиректориях. Название и логотип "MINIX" — товарный знак,
поэтому проект переименован в ReMinix и позиционируется как независимый форк.

## 2. Общий принцип: микроядро + серверы в пространстве пользователя

ReMinix (как и MINIX 3) — классическая микроядерная ОС в духе идей Танненбаума:

- **Ядро** (`minix/kernel`) выполняет только самый необходимый минимум: планирование
  процессов, обработку прерываний/исключений, передачу сообщений (IPC) и низкоуровневый
  доступ к памяти/портам ввода-вывода по запросу привилегированных процессов. Ядро не
  содержит файловых систем, драйверов устройств или сетевого стека.
- **Системные серверы** (`minix/servers`) и **драйверы** (`minix/drivers`) — обычные
  процессы пользовательского пространства с ограниченными привилегиями, которые
  общаются друг с другом и с ядром через синхронный обмен сообщениями (IPC) поверх
  системного вызова `sys_call`/`ipc.h`.
- Сбой драйвера или сервера (кроме нескольких самых базовых) не обязан приводить к
  падению всей системы — за перезапуск отвечает **RS (Reincarnation Server)**.

Это даёт систему, привлекательную для встраиваемых применений: маленькое доверенное
ядро, изоляция отказов, возможность заменять/обновлять компоненты на лету
(`sef_liveupdate.c`).

### 2.1 IPC и таблица сообщений

- `minix/include/minix/ipc.h` (~59 КБ) и `minix/include/minix/com.h` (~49 КБ) — центральные
  заголовки: типы сообщений, номера "звонков" (call numbers), карта endpoint'ов всех
  системных процессов. Именно эти файлы определяют протокол взаимодействия ядра,
  серверов и драйверов и являются машинно-независимыми (архитектурно-специфичен только
  сам механизм передачи сообщения на уровне ядра).
- `minix/kernel/system.c` + `minix/kernel/system/do_*.c` — реализация системных
  "kernel calls" (аналог гипервызовов): копирование памяти, safecopy, IRQ-контроль,
  таймеры, управление привилегиями процессов и т.д. Это машинно-независимый уровень,
  опирающийся на примитивы из `kernel/arch/<arch>/`.
- `minix/servers/ipc` — сервер POSIX IPC (семафоры, разделяемая память) — не путать с
  внутренним микроядерным IPC.

## 3. Дерево `minix/` — специфичные для ОС компоненты

```
minix/
├── kernel/     — микроядро
│   ├── arch/{i386,earm}/   — машинно-зависимый код ядра
│   └── system/             — машинно-независимые kernel calls (do_*.c)
├── servers/    — системные серверы пространства пользователя
│   ├── pm/     — Process Manager (fork/exec/сигналы/планирование процессов верхнего уровня)
│   ├── vfs/    — Virtual File System (файловые дескрипторы, mount, пути, select, сокеты)
│   ├── vm/     — Virtual Memory (таблицы страниц, регионы памяти, обработка page fault)
│   │   └── arch/{i386,earm}/  — машинно-зависимая часть VM (формат page table)
│   ├── rs/     — Reincarnation Server (запуск/перезапуск/live-update сервисов)
│   ├── ds/     — Data Store (простое key-value хранилище для межпроцессного обмена состоянием)
│   ├── sched/  — планировщик пользовательского уровня (квоты, приоритеты)
│   ├── mib/    — Management Information Base (реализация sysctl(7)/proc(5))
│   ├── is/     — Information Server (диагностика/дампы состояния системы)
│   ├── vfs? / ipc/  — POSIX-семафоры и SysV shared memory
│   └── devman/ — Device Manager (перечисление устройств для драйверов)
├── drivers/    — драйверы устройств (userspace), сгруппированы по классам:
│   audio, bus, clock, eeprom, hid, iommu, net, power, printer,
│   sensors, storage, system, tty, usb, video, vmm_guest
├── fs/         — файловые системы как userspace-серверы: mfs (родная MINIX FS),
│                 ext2, isofs, procfs, ptyfs, pfs (pipe fs), hgfs/vbfs (VMware/VirtualBox
│                 shared folders)
├── net/        — сетевой стек: lwip (используется как сетевой сервер) + uds (UNIX sockets)
├── lib/        — библиотеки уровня ОС (см. §3.1)
├── llvm/       — инструментарий LLVM/Clang, используемый тулчейном и "MINIX Magic"
│                 (инструментация для gcov/sprofile/self-healing, см. `libmagicrt`)
├── include/    — публичные заголовки MINIX-специфичных API (`minix/*.h`, `sys/*.h`, `net/*.h`)
└── commands/   — MINIX-специфичные консольные утилиты (MAKEDEV, minix-service,
                  netconf, fdisk, partition, sysenv, readclock, MAKEDEV, ...)
```

### 3.1 Ключевые библиотеки (`minix/lib`)

Библиотечный слой — это то, что превращает "процесс пользователя, слушающий IPC" в
драйвер/файловую систему/сервер по шаблону:

- `libsys` — обёртки над kernel calls (`sys_*.c`), SEF-фреймворк (`sef*.c` — Self
  Healing/State transfer Event Framework: инициализация, обработка сигналов, live update,
  ping/heartbeat), rmib (реализация sysctl-дерева), PCI-доступ (`pci_*.c`).
- `libblockdriver`, `libchardriver`, `libnetdriver`, `libinputdriver`, `libfsdriver`,
  `libaudiodriver`, `libi2cdriver` — библиотеки-скелеты, реализующие стандартный
  жизненный цикл и протокол общения с VFS/сетевым сервером для соответствующего класса
  драйверов; конкретному драйверу остаётся реализовать только колбэки под конкретное
  железо.
- `libddekit` — Device Driver Environment kit (среда для переиспользования драйверов
  из мира Linux/DDE, если применимо).
- `libvirtio` — общий код для virtio-устройств (важно для запуска в виртуалках/QEMU
  при разработке и тестировании портов на новые архитектуры).
- `libusb`, `libgpio`, `libi2cdriver`, `libclkconf` — поддержка шинных протоколов,
  актуальны для встраиваемых плат.
- `libminixfs`, `libvtreefs`, `libpuffs`, `libsffs` — вспомогательные библиотеки для
  файловых серверов.
- `libc`, `libminc`, `libmthread`, `libtimers`, `libbdev`, `libasyn`, `libvassert` —
  системная libc (унаследована и адаптирована из NetBSD) и сопутствующая инфраструктура
  (кооперативные потоки, таймеры, асинхронные блочные запросы).

## 4. Дерево верхнего уровня — наследие NetBSD

Помимо `minix/`, репозиторий устроен как классическое дерево исходников NetBSD (это
видно и по структуре, и по истории коммитов "sync with NetBSD-8"):

| Каталог | Назначение |
|---|---|
| `sys/` | Заголовки и часть кода ядра NetBSD, разделяемая с MINIX (сетевые протоколы `netinet*`, `uvm`, `ufs`, `dev/`, `arch/{i386,x86,arm,evbarm}`). Используется как источник заголовков/протоколов, а не как альтернативное ядро. |
| `common/`, `dist/`, `external/`, `gnu/` | Импортированные сторонние компоненты (GNU-утилиты, BSD-утилиты, внешние библиотеки с "чужими" лицензиями). |
| `lib/`, `include/` | Юзерлендовая libc/системные библиотеки NetBSD и стандартные заголовки (`stdio.h` и т.п.), поверх которых уже лежит `minix/lib`, `minix/include`. |
| `bin/`, `sbin/`, `usr.bin/`, `usr.sbin/`, `libexec/`, `games/` | Стандартные консольные утилиты NetBSD (аналог coreutils). |
| `share/` | share/mk — фреймворк `bmake` (`bsd.*.mk`), man-страницы, шрифты, зоны и т.п. |
| `crypto/` | Криптографические компоненты (есть история про "NOCRYPTO option" — опциональное отключение). |
| `tools/` | Кросс-тулчейн для сборки на хостовой машине: `gcc`, `binutils`, `llvm`/`llvm-clang`/`llvm-lld`/`llvm-tblgen`, `make` (bmake), `mtree`, `makefs`, `installboot`, `pax`, генераторы (`yacc`, `lex`, `mkdep`...). Именно этот тулчейн определяет, под какие машинные триплеты вообще можно собирать систему. |
| `distrib/` | Наборы дистрибутива (`sets`) — списки файлов, попадающих в тот или иной установочный набор. |
| `releasetools/` | Скрипты сборки загрузочных образов — **см. §6, критично для портирования**. |
| `etc/` | Конфигурационные файлы по умолчанию (`rc.conf`, `rc.d/*`, `master.passwd`, `fstab` и т.д.), устанавливаемые в `/etc` целевой системы. |
| `tests/` | Регрессионные тесты (в т.ч. `minix/tests`). |
| `games/` | Игры NetBSD (наследие, не критично для встраиваемого применения). |

## 5. Система сборки

Сборка — классический `make build` в стиле NetBSD (`Makefile` верхнего уровня — почти
дословно `$NetBSD: Makefile,v 1.316`, расширенный директивами `defined(__MINIX)`):

1. `build.sh` — bootstrap-скрипт (аналог `NetBSD/build.sh`), поднимает хостовой
   инструментарий (кросс-компилятор, bmake и т.д.) и запускает `make build`.
2. `_SUBDIR` в корневом `Makefile` перечисляет порядок сборки: `tools lib include gnu
   external crypto/external bin games libexec sbin usr.bin usr.sbin share sys etc tests
   compat .WAIT rescue .WAIT distrib regress`, и — если `defined(__MINIX)` — дополнительно
   `.WAIT minix` (сборка MINIX-специфичных серверов/драйверов идёт последней, после
   готовности `lib/`).
3. Управляющие переменные (`MACHINE`, `MACHINE_ARCH`, `DESTDIR`, `MKX11`, `MKCOMPAT`,
   `MKUNPRIVED`...) читаются из `share/mk/bsd.own.mk` и аналогов — именно `MACHINE`/
   `MACHINE_ARCH` определяют, какая ветка `kernel/arch/`, `servers/*/arch/`, `sys/arch/`
   участвует в сборке.
4. `tools/` собирается первым и содержит весь кросс-тулчейн (в этом дереве уже есть
   LLVM/Clang, а не только GCC — значит, добавление нового target triple в первую очередь
   вопрос конфигурации LLVM/binutils под новый `MACHINE_ARCH`, а не смены компилятора).

## 6. Загрузочные образы и портирование "снизу"

`releasetools/` показывает, что весь процесс создания загружаемого образа сейчас
**жёстко завязан на конкретную архитектуру**:

- `x86_hdimage.sh`, `x86_cdimage.sh`, `x86_usbimage.sh`, `x86_ramimage.sh` — образы для
  x86 (BIOS-загрузка, disklabel/MBR).
- `arm_sdimage.sh` + `fetch_u-boot.sh` + `gen_uEnv.txt.sh` — SD-образ для ARM,
  завязанный на U-Boot и конкретную плату (см. §7).
- Общая инфраструктура (`image.functions`, `image.defaults`, `release.sh`,
  `release.functions`, `mkboot`) частично архитектурно-независима, но точки входа —
  нет.

Для новой архитектуры потребуется свой `<arch>_*image.sh` (или обобщение существующих
скриптов), а также решение по загрузчику (BIOS/UEFI для amd64, U-Boot/EFI для
arm64/riscv64/mips64).

## 7. Текущая поддержка архитектур (по факту в коде)

На момент этой сессии реально поддерживаются **две** архитектуры, и обе видны в трёх
параллельных местах дерева, которые обязательно нужно продублировать для любой новой
архитектуры:

| Место | `i386` | `earm` |
|---|---|---|
| `minix/kernel/arch/<arch>/` | развитый x86-порт: APIC, ACPI, SMP, breakpoints, отдельный `Makefile.inc` | ARMv7-порт, специфичный для **TI OMAP** (`earm/bsp/ti/*`, только один BSP — судя по всему, BeagleBone/аналог) |
| `minix/servers/vm/arch/<arch>/` | `pagetable.h` + `Makefile.inc` | то же самое, свой формат таблиц страниц |
| `sys/arch/` (унаследовано из NetBSD) | `i386/`, `x86/` (общий x86-код) | `arm/`, `evbarm/` |

Важные наблюдения для планирования портирования:

- Даже унаследованное из NetBSD дерево `sys/arch/` **не содержит** `amd64/`, `aarch64`
  (`arm64/` в терминах NetBSD), `riscv/`, `mips/` — при полном сохранении подхода "берём
  заголовки/код из NetBSD" эти каталоги нужно будет **импортировать из апстрима NetBSD**
  отдельно (это большая работа сама по себе, и версии придётся выравнивать с уже
  используемой NetBSD-8 базой или мигрировать выше).
- `earm` реализует только один BSP (TI OMAP через `bsp/ti`) — то есть "arm32" в этом
  дереве де-факто означает "один конкретный SoC", а не общий ARMv7. Обобщение ARM-порта
  на другие SoC (или его переиспользование как основы для отдельного generic `arm32`)
  — тоже часть работы, отдельная от добавления aarch64.
- Тулчейн (`tools/`) уже несёт LLVM/Clang — хороший знак для мультиархитектурности
  (Clang изначально мультитаргетный), но `binutils`/`gcc`/сборочные профили всё равно
  нужно сконфигурировать под новые триплеты.
- `minix/llvm/passes` — LLVM-проходы, используемые сборкой (инструментация,
  "MINIX Magic"/самолечение) — при портировании toolchain нужно проверить, что эти
  проходы не завязаны неявно на x86/ARM specifics.
