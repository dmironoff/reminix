# ReMinix — управление памятью: текущее устройство и целевая архитектура

> Долгоживущий design-документ. Описывает, как память устроена в унаследованном
> MINIX 3, и целевую архитектуру управления памятью для этапа модернизации
> (`docs/modernization.md`, п. 2, 3, 5, 7). Обновляйте, когда меняется суть решения.
> Прогресс внедрения ведите в `docs/handoff.md`.
>
> **Статус:** проект, принят за основу владельцем проекта 2026-09-25. Детали ABI
> (размеры полей, лимиты, номера вызовов) уточняются при реализации. Уточнения
> вносите сюда.

## 0. Кратко

Главный вывод из разбора кода: разделение ролей в MINIX 3 **правильное**. Ядро ведёт
раннюю карту памяти. VM-сервер ведёт постраничный физический аллокатор и логические
регионы процессов. Неправильно другое: 32-битные предположения, линейный поиск в
аллокаторе и то, что **VM сам пишет аппаратные таблицы страниц**. Из-за последнего в
VM оказывается архитектурно-зависимый код.

Цель — сохранить разделение ролей и заменить слабые места:

```
             ┌──────────────────────────── VM-сервер ────────────────────────────┐
             │ Уровень 2: регионы (vir_region / phys_region / phys_block,        │
             │            mem_type: anon, contig, directphys, shared, cache)     │
             │                 │  pm_alloc / pm_free          │ apt_map/unmap   │
             │ Уровень 1: физический аллокатор   Уровень 3 (VM): журнал         │
             │            buddy по реальным банкам   отображений (APT), без       │
             │            RAM, 64-битные адреса      знания формата MMU           │
             └──────────────────────────▲───────────────────────┬────────────────┘
                 kinfo: карты memory/reserved      общая память + kmutex,
                                        │          VMCTL_AS_SYNC
             ┌──────────────────────────┴──────── ядро ─────────▼────────────────┐
             │ Уровень 0: bootmem — ранняя        Уровень 3 (ядро): объект        │
             │ карта memory[] + reserved[]        адресного пространства kas,     │
             │ по FDT / multiboot                 потребитель журнала, ASID       │
             │                                           │ arch_pt_*()           │
             │                              minix/kernel/arch/<arch>/ — транслятор│
             │                              в аппаратные таблицы + TLB            │
             └────────────────────────────────────────────────────────────────────┘
```

| Уровень | Где | Что делает | Заменяет |
|---|---|---|---|
| 0. bootmem | ядро | карта «что есть» и «что занято» на время загрузки | `add_memmap` / `cut_memmap` / `pg_alloc_page` |
| 1. физический аллокатор | VM | выдаёт страницы и непрерывные блоки 2ⁿ страниц | битовая карта `alloc.c` на 4 ГБ |
| 2. регионы | VM | логическое адресное пространство, COW, типы памяти | остаётся, с исправлением типов |
| 3. APT | VM → ядро | абстрактные операции отображения → аппаратные таблицы | архитектурная часть `pagetable.c` и `vm/arch/*` |

## 1. Как устроено сейчас (MINIX 3, до модернизации)

Разобрано по коду ReMinix (VM-сервер пока не менялся относительно MINIX 3).

### 1.1 Ранний этап: ядро

- `pre_init` получает карту RAM от загрузчика: multiboot на i386, эмуляция
  multiboot с жёсткими 256 МБ на earm (см. `docs/arch-earm.md`). Карта заносится в
  `kinfo.memmap[]` через `add_memmap()`. Занятое вырезается `cut_memmap()`
  (`minix/kernel/arch/*/pg_utils.c`).
- Страницы под себя, прежде всего под таблицы страниц, ядро берёт через
  `pg_alloc_page()`. Это bump-аллокатор: он откусывает страницу с начала первого
  непустого участка `memmap` и увеличивает `kernel_allocated_bytes_dynamic`.
- `arch_boot_proc()` (`arch/*/protect.c`) загружает ELF VM из модуля в выделенные
  страницы, затем возвращает память модуля в карту
  (`add_memmap(mod_start…)`). Модули остальных загрузочных процессов остаются
  занятыми, их потом отображает VM.
- Итог передаётся VM через `sys_getkinfo()`.

### 1.2 Физический аллокатор VM: `minix/servers/vm/alloc.c`

- `get_mem_chunks()` превращает `kinfo.memmap` в `mem_chunks[NR_MEMS]`, выравнивая
  до страниц. `mem_init()` помечает эти участки свободными.
- Структура данных — **битовая карта**, один бит на страницу 4 КБ. Размер
  рассчитан ровно на 32-битное пространство
  (`NUMBER_PHYSICAL_PAGES = 0x100000000ULL / VM_PAGE_SIZE`), это 128 КБ.
  Номера страниц хранятся в `int`.
- `free_page_cache[10000]` — стек недавно освобождённых страниц. Одиночная
  страница выдаётся из него за O(1).
- `alloc_pages()` в остальных случаях ищет first-fit (`findbit`) **сверху вниз** от
  `lastscan`. Флаги:
  - `PAF_CLEAR` — обнуление через `sys_memset`;
  - `PAF_ALIGN16K` / `PAF_ALIGN64K` — выделение с запасом и освобождение лишней
    головы. 16 КБ нужно под L1-таблицу ARM;
  - `PAF_LOWER16MB` / `PAF_LOWER1MB` — ограничения для DMA на x86.
- Если памяти не хватает, `alloc_mem()` вызывает `cache_freepages()`, выселяя
  файловый кэш, и повторяет попытку.
- Отладка: `SANITYCHECKS` ведёт `pagemap[]` (место выделения каждой страницы),
  `JUNKFREE` заполняет освобождённую память мусором.

### 1.3 Память для самого VM

- `vm_allocpage()` (`pagetable.c`): чтобы отобразить страницу себе, VM может
  понадобиться ещё одна страница под таблицу страниц. Отсюда рекурсия.
  - До `pt_init()` или при вложенном вызове страница берётся из статических
    **запасных страниц** (`static_sparepages[]`, 15–190 штук в зависимости от
    архитектуры) и отдельных запасных каталогов.
  - В остальных случаях: `alloc_mem()`, затем `vm_mappages()`.
- Резервные очереди (`reservedqueue_*`) держат заранее выделенные и отображённые
  страницы. `alloc_cycle()` пополняет их в главном цикле.
- Внутренние объекты VM (регионы, `phys_region`, `phys_block`) выделяются
  slab-аллокатором (`slaballoc.c`, классы 8…~207 байт) на страницах из
  `vm_allocpage(VMP_SLAB)`.

### 1.4 Логическая память процессов

```
vmproc
 └─ AVL-дерево vir_region            (vaddr, length, flags, def_memtype)
      └─ physblocks[]                 указатель на каждую страницу региона
           └─ phys_region            (offset, memtype, next_ph_list)
                └─ phys_block        (phys, refcount: u8, firstregion)
```

Поведение задаётся таблицей методов `mem_type_t`:

| Тип | Файл | Когда выделяется физическая память |
|---|---|---|
| anon | `mem_anon.c` | лениво, по одной странице в `anon_pagefault` |
| anon_contig | `mem_anon_contig.c` | сразу, непрерывным блоком (DMA) |
| directphys | `mem_directphys.c` | никогда: отображается заданный физический адрес (MMIO) |
| shared | `mem_shared.c` | берётся из региона другого процесса |
| cache / file | `mem_cache.c`, `mem_file.c`, `cache.c` | страницы файлового кэша VM (mmap файлов) |

- **Page fault:** ядро → сообщение VM → `map_pf` → `ev_pagefault` → `alloc_mem(1)` →
  `pt_writemap` → `sys_vmctl` снимает блокировку с процесса.
- **fork** (`map_proc_copy`): `phys_block` становятся общими (`refcount++`) и
  доступными только на чтение. `mem_cow` копирует страницу при записи.

### 1.5 Таблицы страниц

VM строит аппаратные таблицы каждого процесса (`pt_t`, `pt.h`) **сам** и пишет их
напрямую, держа их отображёнными у себя. Ядро получает только корень
(`VMCTL_SETADDRSPACE`), сбрасывает TLB (`VMCTL_FLUSHTLB`) и копирует себе нужные
отображения. Отсюда ~50 ветвлений `__i386__` / `__arm__` в `pagetable.c` и каталог
`vm/arch/`.

### 1.6 Ограничения, которые снимает модернизация

| Ограничение | Где | Следствие |
|---|---|---|
| Битовая карта ровно на 4 ГБ, номера страниц в `int` | `alloc.c` | не работает на 64-битных платформах и с памятью выше 4 ГБ |
| Линейный поиск непрерывных блоков | `alloc.c:findbit` | медленное выделение для DMA и L1-таблиц при большом объёме RAM |
| Выравнивание через перевыделение | `alloc_mem` | лишняя работа, фрагментация |
| `refcount` имеет тип `u8_t` | `region.h` | не больше 255 ссылок на страницу |
| VM пишет аппаратные таблицы | `pagetable.c`, `vm/arch/` | каждый новый порт приходится делать в VM |
| Жёсткая карта памяти на earm | `arch/earm/pre_init.c` | нет Device Tree, нет нескольких банков |
| Полный сброс TLB при смене АП | ядро, VMCTL | нет ASID (п. 5 модернизации) |

## 2. Принципы целевой архитектуры

1. **Политику определяет VM, механизм — ядро.** VM решает, что и куда отображать.
   Ядро только транслирует решения VM в аппаратный формат и обслуживает TLB.
   После загрузки ядро **не выделяет** физическую память по своей инициативе.
2. **Формат MMU известен только в `minix/kernel/arch/<arch>/`.** VM оперирует
   абстрактными операциями: адрес, длина, права, тип кэширования.
3. **Через границу ядро–VM не передаются указатели.** Общие структуры адресуются
   индексами и смещениями, поля имеют фиксированную ширину: физические адреса в
   общих структурах — `uint64_t` на всех архитектурах (задел под LPAE и PAE).
   Внутри ядра и VM — типы схемы `docs/types-audit.md` §9а (решение 2026-10-07):
   `phys_addr_t` шириной платформы (64 бита при `CONFIG_PHYS_ADDR_64`), `pfn_t`,
   `vir_addr_t`, `dma_addr_t`, длины — `size_t`.
4. **Операции, расширяющие права, применяются лениво, сужающие — синхронно.**
   Отображение новой страницы можно применить при следующем запуске процесса.
   Снятие отображения или понижение прав должно завершиться, включая сброс TLB
   на всех CPU, до того как VM переиспользует страницу. Это правило даёт
   корректность на SMP и при многопоточности.
5. **Каждый уровень можно тестировать отдельно.** bootmem, buddy и кодировщик
   журнала — чистый C без зависимостей, с тестами на хосте.
6. **RAM и MMIO не смешиваются.** Карты памяти описывают только RAM. Устройства
   описываются FDT (`reg` у узлов) и отображаются как `directphys` с типом
   кэширования `DEVICE`.

## 3. Уровень 0: ранняя карта памяти ядра (bootmem)

Аналог memblock в Linux, но минимальный. Работает от `pre_init` до передачи
управления VM.

### 3.1 Структуры (ABI `kinfo`, общий для ядра и VM)

```c
/* minix/include/minix/bootmem.h */
typedef uint64_t phys_addr_t;	/* тип под вопросом: принцип 3, §10 вопрос 7 */

struct bm_region {
	phys_addr_t base;
	phys_addr_t size;
	uint32_t    type;      /* для reserved: BM_KERNEL, BM_BOOTMOD, ... */
	uint32_t    flags;     /* BM_F_NOMAP — не отображать (память прошивки) */
};

#define BM_MAX_MEMORY    32
#define BM_MAX_RESERVED  64

struct bm_map {
	uint32_t nmemory, nreserved;
	struct bm_region memory[BM_MAX_MEMORY];     /* ЧТО ЕСТЬ: банки RAM */
	struct bm_region reserved[BM_MAX_RESERVED]; /* ЧТО ЗАНЯТО */
};
```

- Оба массива **отсортированы по `base`**, соседние записи с одинаковыми `type` и
  `flags` склеиваются. Свободная память = `memory − reserved`, отдельно не хранится.
- Ёмкость фиксированная (статический массив в `kinfo`), без динамического роста.
  Для встраиваемых систем этого с запасом хватает. При переполнении — `panic` с
  понятным сообщением.
- Типы в `reserved`: `BM_KERNEL`, `BM_BOOTMOD`, `BM_FDT`, `BM_FIRMWARE`
  (`/memreserve/`, `/reserved-memory`, код PSCI/OP-TEE), `BM_KERNEL_PT`,
  `BM_APT_ARENA`, `BM_TRAMPOLINE`, `BM_BOOTINFO`, `BM_KERNEL_DYN` (прочее,
  выделенное ядром при загрузке).

### 3.2 API (только ядро, только до запуска VM)

```c
void        bm_add(phys_addr_t base, phys_addr_t size, uint32_t flags);   /* RAM */
void        bm_remove(phys_addr_t base, phys_addr_t size);                /* mem= и т.п. */
void        bm_reserve(phys_addr_t base, phys_addr_t size, uint32_t type);
phys_addr_t bm_alloc(phys_addr_t size, phys_addr_t align, uint32_t type); /* сверху вниз */
phys_addr_t bm_alloc_below(phys_addr_t size, phys_addr_t align,
                           phys_addr_t limit, uint32_t type);              /* trampoline x86 */
void        bm_seal(void);   /* после этого bm_alloc → panic */
```

Код общий для всех архитектур: `minix/kernel/bootmem.c`, около 300 строк.
Архитектура и BSP только поставляют данные.

### 3.3 Заполнение

| Источник | Что вызывается |
|---|---|
| FDT `/memory` (все банки, с учётом `#address-cells` / `#size-cells`) | `bm_add` |
| FDT `/memreserve/`, `/reserved-memory` | `bm_reserve(BM_FIRMWARE)`, для `no-map` — ещё флаг `BM_F_NOMAP` |
| сам DTB, образ ядра, ramdisk с модулями (fitImage, п. 6) | `bm_reserve` |
| i386 на переходный период: multiboot mmap | `bm_add` / `bm_reserve`, пока не сделан п. 6 |

FDT разбирается ядерной сборкой libfdt (`docs/modernization.md` п. 10) в
`pre_init`, до включения страничной адресации.

После этого ядро выделяет через `bm_alloc`: таблицы страниц ядра, стеки CPU,
trampoline, арену APT (§6.2), стартовый пул страниц для таблиц (§6.5) и память для
загрузки VM. Затем `bm_seal()`, и `bm_map` уходит VM через `kinfo`.

### 3.4 Что делает с картой VM

- Все банки `memory[]` получают дескрипторы страниц (§4).
- Всё из `reserved[]` помечается занятым. `BM_BOOTMOD` освобождаются, когда
  соответствующий процесс загружен (как сейчас). `BM_KERNEL*`, `BM_APT_ARENA`,
  `BM_FIRMWARE` остаются занятыми навсегда.
- Статистика «всего памяти» считается честно из `memory[]`, без поправок, которые
  сейчас делает `main.c` VM (`mem_add_total_pages`).

## 4. Уровень 1: физический аллокатор VM (buddy)

Заменяет битовую карту `alloc.c`. Внешний интерфейс `alloc_mem()` / `free_mem()`
остаётся как тонкая обёртка, поэтому код регионов на первом шаге не меняется.

### 4.1 Дескриптор страницы и сегменты

```c
/* minix/servers/vm/physmem.h */
typedef uint64_t pfn_t;                 /* номер физической страницы */

struct vm_page {                        /* 16 байт, 0,4 % от объёма RAM */
	uint32_t next, prev;            /* индексы в списке свободных (в пределах сегмента) */
	uint16_t flags;                 /* PG_FREE_HEAD, PG_RESERVED, PG_ALLOCATED, ... */
	uint8_t  order;                 /* порядок, если PG_FREE_HEAD */
	uint8_t  zone;
	uint32_t aux;                   /* задел: refcount (п. 4.5) */
};

struct memseg {                         /* один банк RAM из kinfo.memory[] */
	pfn_t           start_pfn;
	uint32_t        npages;
	struct vm_page *pages;          /* массив дескрипторов */
	struct free_area {
		uint32_t head;          /* индекс первого свободного блока или NIL */
		uint32_t count;
	} free[PM_MAX_ORDER + 1];
};
```

- **Где лежат дескрипторы.** Массив `vm_page[]` каждого сегмента размещается в
  памяти, которую VM получает на старте. VM выделяет её из самого сегмента, в
  начале его свободной части, и отображает себе. Этот участок помечается
  `PG_RESERVED`.
- **Связи хранятся индексами, а не указателями.** Структура остаётся одинаковой
  для 32 и 64 бит, её проще проверять и выводить при отладке.
- **Buddy на каждый сегмент отдельный.** Блок никогда не пересекает границу банка,
  а номер двойника вычисляется как `pfn ^ (1 << order)` относительно **нуля
  физических адресов**, поэтому выравнивание блоков реальное.
- `PM_MAX_ORDER` = 10 (блоки до 4 МБ при странице 4 КБ). Можно поднять до 18 для
  гигантских страниц aarch64/riscv64, если это понадобится APT (§6.6).

### 4.2 Инициализация

Для каждого сегмента: все страницы помечаются `PG_RESERVED`, затем для каждого
свободного участка (`memory − reserved`) выполняется жадная нарезка. С текущего
адреса берётся наибольший блок, который выровнен на свой размер и помещается в
остаток. Каждый такой блок освобождается через обычный `pm_free`, и слияние
отрабатывает само.

### 4.3 API

```c
phys_addr_t pm_alloc(unsigned order, int flags);          /* блок 2^order страниц */
phys_addr_t pm_alloc_pages(size_t npages, int flags);     /* точно: хвост возвращается */
void        pm_free(phys_addr_t pa, unsigned order);
void        pm_free_pages(phys_addr_t pa, size_t npages);
void        pm_stats(struct pm_stats *st);                /* свободно по порядкам */

/* флаги */
#define PMF_CLEAR   0x01   /* обнулить (sys_memset) */
#define PMF_DMA     0x02   /* зона DMA (см. 4.4) */
#define PMF_NOWAIT  0x04   /* не выселять файловый кэш */
```

- **Выделение.** Взять блок из `free[order]`. Если список пуст, найти первый
  непустой список большего порядка и делить блок, пока не получится нужный
  порядок. Сложность O(`PM_MAX_ORDER`).
- **Освобождение.** Пока двойник помечен `PG_FREE_HEAD` и имеет тот же порядок,
  изъять его из списка и слить. Затем вставить результат.
- **Выравнивание получается само.** L1-таблица ARM (16 КБ) — блок `order 2`,
  64 КБ — `order 4`. Флаги `PAF_ALIGN16K` / `PAF_ALIGN64K` превращаются в порядок.
- **Нехватка памяти.** Как сейчас: `cache_freepages()` и повтор, если не задан
  `PMF_NOWAIT`.
- **Кэш одиночных страниц.** На первом этапе не нужен, потому что VM
  однопоточный. После п. 8, если VM станет многопоточным, можно добавить
  per-thread или per-CPU кэши order 0, как `pcp` в Linux.

### 4.4 Зоны

- `ZONE_NORMAL` — вся память.
- `ZONE_DMA` — память ниже предела, который задаёт платформа: `dma-ranges` из
  FDT, на i386 — 16 МБ. Реализуется как отдельный набор сегментов (сегмент режется
  по границе зоны при инициализации). `PAF_LOWER16MB` отображается в `PMF_DMA`.
- `PAF_LOWER1MB` (i386, только trampoline) переходит в ядро: trampoline
  выделяется через `bm_alloc_below` на этапе bootmem. У VM этот флаг исчезает.

### 4.5 Счётчик ссылок

- **Шаг 1.** `phys_block.refcount`: `u8_t` → `uint32_t`. Это минимальная правка.
- **Шаг 2, опционально.** Перенести счётчик в `vm_page.aux`. Тогда `phys_block`
  можно облегчить или заменить прямыми ссылками на страницы. Решение принимать
  по результатам измерений (§10).

### 4.6 Проверки

`SANITYCHECKS` переходят на дескрипторы. Каждая страница находится ровно в одном
из состояний: свободна (внутри блока), выделена или зарезервирована. Проверка
обходит все сегменты и сверяет состояния со списками свободных. Модуль buddy
(`physmem.c`) компилируется и на хосте, тесты на случайных последовательностях
alloc/free сверяются с эталонной битовой картой.

## 5. Уровень 2: регионы VM

Архитектура `vir_region` / `phys_region` / `phys_block` / `mem_type_t` сохраняется,
она не зависит от формата MMU. Меняется следующее:

| Что | Изменение | Связь |
|---|---|---|
| `phys_bytes`, `vir_bytes` в структурах VM | 64-битные адреса (`phys_addr_t`), виртуальные — по разрядности платформы | п. 7 |
| `phys_block.refcount` | `uint32_t` | §4.5 |
| выделение памяти | `alloc_mem` → `pm_alloc*` | §4 |
| запись в таблицы (`pt_writemap`, `pt_ptalloc`, `pt_mapkernel`, …) | вызовы журнала `apt_map` / `apt_unmap` / `apt_protect` + `apt_sync` | §6 |
| `vmproc.vm_pt` (аппаратная таблица) | идентификатор адресного пространства `as_id` | §6, п. 8 |
| владение адресным пространством | объект «адресное пространство» со счётчиком ссылок, общий для потоков одного процесса | `docs/threads.md` |
| `physblocks[]` (указатель на каждую страницу региона) | на первом этапе без изменений; позже — разреженная структура (radix), если накладные расходы станут заметны | §10 |

Память для самого VM упрощается. VM больше не выделяет страницы под **таблицы
страниц**: это делает ядро из пула (§6.5). Поэтому рекурсия «чтобы отобразить
страницу, нужна страница под таблицу» исчезает. Механизм `static_sparepages` и
резервные очереди сводятся к поддержке пула таблиц ядра и небольшому запасу
страниц для slab.

## 6. Уровень 3: абстрактные таблицы страниц (APT)

### 6.1 Идея

APT — это **журнал абстрактных операций отображения** для каждого адресного
пространства (АП). VM пишет операции в общую с ядром память. Ядро применяет их к
аппаратным таблицам через архитектурный транслятор. По смыслу это интерфейс
`pmap` из NetBSD/BSD (`pmap_enter`, `pmap_remove`, `pmap_protect`, `pmap_update`),
вынесенный через границу ядро–сервер и собираемый в пакеты, чтобы не делать
ловушку в ядро на каждую страницу.

Полное описание отображений по-прежнему хранит VM, в своих регионах. Ядро хранит
аппаратные таблицы как **производное состояние**. Их всегда можно сбросить и
восстановить повтором операций из VM (`VMCTL_AS_RESET`, §6.4). Это важно для
перезапуска и live update VM.

### 6.2 Общая память: арена APT

- При загрузке ядро выделяет через `bm_alloc` **арену** из `NR_AS` страниц
  (`NR_AS` = `NR_PROCS`, отдельное АП для каждого процесса; потоки п. 8
  разделяют АП). Страница `i` — журнал адресного пространства с `as_id = i`.
- Ядро отображает арену в свою часть адресного пространства навсегда. VM получает
  её физический адрес через `kinfo` и отображает себе при инициализации. Обе
  стороны адресуют журналы только номером `as_id`.

```c
/* minix/include/minix/apt.h — общий ABI ядра и VM */
enum { APT_OP_MAP = 1, APT_OP_UNMAP, APT_OP_PROTECT };

#define APT_R     0x01
#define APT_W     0x02
#define APT_X     0x04
#define APT_U     0x08     /* доступ из пользовательского режима */
#define APT_G     0x10     /* глобальное (не зависит от ASID) — только для ядра */

enum apt_cache {           /* тип памяти; транслятор отображает на MAIR/TEX/PAT/PBMT */
	APT_C_WB = 0,      /* обычная память, write-back */
	APT_C_WT,          /* write-through */
	APT_C_WC,          /* write-combining (framebuffer) */
	APT_C_UC,          /* некэшируемая обычная */
	APT_C_DEVICE,      /* устройство, строгий порядок */
};

struct apt_op {            /* 32 байта, одинаково на 32 и 64 бит */
	uint16_t op;
	uint16_t prot;     /* APT_R|W|X|U|G */
	uint16_t cache;    /* enum apt_cache */
	uint16_t flags;    /* задел: APT_F_HUGE_OK и т.п. */
	uint32_t npages;
	uint32_t _pad;
	uint64_t va;
	uint64_t pa;       /* для MAP: начало физически непрерывного участка */
};

#define APT_JOURNAL_OPS  126

struct apt_journal {       /* ровно одна страница 4 КБ */
	kmutex_t  lock;              /* п. 2 модернизации, см. 6.3 */
	uint32_t  as_id;
	uint32_t  generation;        /* растёт при AS_CREATE/RESET этого слота */
	uint64_t  head_seq;          /* пишет VM: номер следующей операции */
	uint64_t  applied_seq;       /* пишет ядро: всё до него применено */
	uint32_t  flags;             /* ядро: APT_J_NEED_PTPAGES и т.п. */
	uint8_t   _pad[28];
	struct apt_op ops[APT_JOURNAL_OPS];   /* кольцо, индекс = seq % APT_JOURNAL_OPS */
};
```

Размеры и число операций на страницу окончательно проверяются
`CTASSERT(sizeof(struct apt_journal) <= 4096)`.

### 6.3 Протокол и роль `kmutex`

**Со стороны VM, запись пакета:**
1. `kmutex_lock(&j->lock)`.
2. Записать операции в `ops[head_seq % N …]`.
3. Барьер release, затем `head_seq += n`.
4. `kmutex_unlock`.

Если кольцо заполнено (`head_seq − applied_seq == N`), VM вызывает
`VMCTL_AS_SYNC` и продолжает.

**Со стороны ядра, применение** (в ядре только `kmutex_trylock`, ядро никогда не
ждёт):

- **Лениво.** В `switch_to_user`: если у АП процесса `applied_seq != head_seq`,
  сделать `trylock`. Удалось — применить операции `(applied_seq, head_seq]`,
  обновить `applied_seq`, отпустить. **Не удалось** — VM прямо сейчас пишет пакет.
  Процесс запускается со старыми таблицами. Это безопасно по принципу 4: все
  сужающие операции к этому моменту уже применены синхронно, а неприменённые
  расширяющие дадут в худшем случае page fault. VM увидит, что страница уже
  отображена, и выполнит `VMCTL_AS_SYNC`. Очереди готовых процессов при этом не
  трогаются.
- **Синхронно.** `VMCTL_AS_SYNC(as_id, upto_seq)` — kernel call от VM. Ядро
  применяет журнал до `upto_seq`, затем сбрасывает TLB по ASID этого АП на всех
  CPU из `as->cpu_mask` (п. 4 и 5). Возвращает управление только после этого.
  Вызов сделан VM, поэтому мьютекс VM уже отпустил и `trylock` проходит. Если
  `trylock` не прошёл (после п. 8, при многопоточном VM), ядро возвращает `EAGAIN`,
  и VM повторяет вызов.

**Для чего нужен `kmutex`.** Если в журнал пишет один поток VM, а читает ядро,
кольцу хватило бы барьеров. `kmutex` нужен для двух вещей:
1. атомарность пакета: ядро не видит половину пакета, например MAP без парного
   UNMAP при перемещении страницы;
2. несколько писателей в один журнал после п. 8, когда VM становится
   многопоточным.

Мьютекс, брошенный упавшим VM, ядро освобождает через `force_unlock` при
перезапуске VM (RS).

**Правило для VM** (принцип 4): физическую страницу, с которой снято отображение,
можно вернуть в buddy только после `VMCTL_AS_SYNC`, покрывающего соответствующий
UNMAP. VM собирает такие страницы в список отложенного освобождения с пометкой
`seq` и возвращает их пакетом после синхронизации.

Какие операции требуют синхронизации:

| Операция VM | Режим |
|---|---|
| отобразить новую страницу (page fault, `mmap` с `MAP_POPULATE`) | лениво; перед ответом на page fault — `sync`, если процесс многопоточный (п. 8) |
| снять отображение (`munmap`, выход, выселение из кэша) | **sync**, до освобождения страниц |
| понизить права (COW при `fork`, `mprotect` на чтение) | **sync**, до продолжения родителя или других потоков |
| повысить права, заменить страницу после COW | MAP поверх; для замены физического адреса — **sync** (старую страницу видят TLB) |

### 6.4 Kernel calls (замена архитектурных `VMCTL_*`)

| Вызов | Что делает | Заменяет |
|---|---|---|
| `VMCTL_AS_CREATE(→ as_id)` | новое АП: корень таблицы из пула (§6.5), журнал обнуляется, `generation++` | выделение `pt_t` в VM |
| `VMCTL_AS_DESTROY(as_id)` | вернуть страницы таблиц в пул, освободить ASID | `pt_free` |
| `VMCTL_AS_BIND(endpoint, as_id)` | привязать процесс (или LWP, п. 8) к АП | `VMCTL_SETADDRSPACE` |
| `VMCTL_AS_SYNC(as_id, upto_seq)` | применить журнал и сбросить TLB, синхронно | `VMCTL_FLUSHTLB`, прямые записи VM в таблицы |
| `VMCTL_AS_RESET(as_id)` | сбросить аппаратные таблицы АП; VM затем воспроизводит отображения | — (новое, для перезапуска и live update VM) |
| `VMCTL_PT_POOL_ADD(pa, order, count)` | отдать ядру страницы под таблицы | `vm_allocpage(VMP_PAGETABLE)` |
| `VMCTL_PT_POOL_RECLAIM(max)` | забрать неиспользуемые страницы пула | — |

Остаются как есть: `VMCTL_CLEAR_PAGEFAULT`, `VMCTL_MEMREQ_GET/REPLY`,
`VMCTL_VMINHIBIT_SET/CLEAR`, `VMCTL_BOOTINHIBIT_CLEAR`. Уходят: `VMCTL_GET_PDBR`,
`VMCTL_SETADDRSPACE`, `VMCTL_FLUSHTLB`, `VMCTL_I386_*`, `VMCTL_KERN_PHYSMAP`,
`VMCTL_KERN_MAP_REPLY`.

### 6.5 Память под аппаратные таблицы: пул ядра

- Ядро **не выделяет** страницы само. VM отдаёт ему страницы из buddy через
  `VMCTL_PT_POOL_ADD`. Размер и выравнивание корневой таблицы архитектура
  сообщает через `kinfo`: `pt_root_order` — 2 для L1 ARMv7 (16 КБ), 0 для
  остальных.
- Пул разделён на два класса: корни (`pt_root_order`) и таблицы нижних уровней
  (order 0). На ARMv7 L2-таблица занимает 1 КБ, поэтому транслятор кладёт четыре
  таких таблицы в одну страницу (упаковка — внутреннее дело `arch/earm`).
- Стартовый пул выделяется через `bm_alloc` при загрузке, его хватает на таблицы
  VM и загрузочных процессов.
- Когда пул опускается ниже порога, ядро выставляет `APT_J_NEED_PTPAGES`, а
  `VMCTL_AS_SYNC` возвращает `ENOSPC`. VM пополняет пул в главном цикле, как
  сейчас `alloc_cycle()`, и повторяет вызов. При ленивом применении с пустым
  пулом ядро помечает процесс `RTS_VMREQUEST` и уведомляет VM. Механизм запросов
  к VM уже есть в ядре (`p_vmrequest`).
- Ядро пишет в страницы таблиц:
  - на 64-битных платформах — через **прямое отображение** всей RAM в верхней
    половине АП ядра;
  - на 32-битных (i386, arm32) — через временные окна отображения на каждом CPU
    (аналог `kmap_atomic`; в MINIX уже есть механизм окон в
    `arch/*/memory.c:createpde`).

### 6.6 Архитектурный интерфейс ядра

Всё, что знает формат MMU, находится в `minix/kernel/arch/<arch>/pt.c`:

```c
/* minix/kernel/arch/<arch>/include/arch_pt.h — реализует каждая архитектура */
int  arch_as_init(struct kas *as);                 /* корень из пула, ядерная часть */
void arch_as_fini(struct kas *as);                 /* вернуть таблицы в пул */
int  arch_pt_map(struct kas *as, uint64_t va, uint64_t pa, uint32_t npages,
                 unsigned prot, unsigned cache, unsigned flags);
int  arch_pt_unmap(struct kas *as, uint64_t va, uint32_t npages);
int  arch_pt_protect(struct kas *as, uint64_t va, uint32_t npages, unsigned prot);
int  arch_pt_lookup(struct kas *as, uint64_t va, uint64_t *pa, unsigned *prot);
void arch_as_activate(struct kas *as);             /* TTBR0 / CR3 / satp + ASID */
void arch_tlb_inval(struct kas *as, uint64_t va, uint32_t npages); /* npages=0 — всё АП */
```

- **Крупные отображения.** Транслятор сам использует блочные отображения, если
  диапазон `va` / `pa` выровнен и `APT_F_HUGE_OK` разрешает это: секции 1 МБ на
  ARMv7, 2 МБ и 1 ГБ на aarch64 и x86-64, мегастраницы на riscv64.
- **`arch_pt_lookup`** заменяет обход аппаратных таблиц в `vm_lookup` и `umap_*`,
  которыми ядро пользуется при копировании между АП.
- **Ядерная часть АП** не входит в журналы процессов:
  - ARMv7 — TTBR1 (`TTBCR.N`) для ядра, TTBR0 для процесса;
  - aarch64 и riscv64 — верхняя половина АП;
  - i386 и x86-64 — `arch_as_init` копирует ядерные записи верхнего уровня в
    каждый новый корень.
- **MMIO-устройства ядра** (UART, контроллер прерываний, таймер BSP) ядро
  отображает само при загрузке по данным FDT. Механизм `kern_phys_map` с
  обратным вызовом из VM больше не нужен.

Общая часть ядра — `minix/kernel/kas.c`: объект адресного пространства и
применение журнала.

```c
struct kas {                        /* по одному на as_id */
	uint32_t   as_id, generation;
	uint32_t   refcount;            /* сколько struct proc (LWP) привязано */
	bitchunk_t cpu_mask[...];       /* где АП активно или может быть в TLB (п. 4) */
	proc_context_id_t ctx;          /* ASID / PCID (п. 5) */
	uint64_t   applied_seq;
	struct arch_as arch;            /* корень таблицы, списки страниц пула и т.п. */
};
```

`struct proc` получает указатель `p_as` вместо архитектурных `p_seg.p_cr3` /
`p_ttbr`. Несколько LWP одного процесса указывают на один `kas` (п. 8).

### 6.7 Загрузка

1. `pre_init`: bootmem (§3). Ядро строит своё отображение, выделяет арену APT,
   стартовый пул таблиц, `kas` для VM.
2. `arch_boot_proc`: ELF VM загружается в страницы из `bm_alloc`, отображения VM
   ядро **само** записывает в `kas` VM через `arch_pt_map` (журнал не нужен).
   `bm_seal()`.
3. VM стартует, читает `kinfo` (`bm_map`, арена, `pt_root_order`), строит buddy,
   отображает себе арену. Для отображения собственных страниц дальше VM
   пользуется своим журналом (`as_id` VM) и `VMCTL_AS_SYNC`.
4. VM создаёт АП остальных загрузочных процессов (`VMCTL_AS_CREATE` +
   `VMCTL_AS_BIND`), отображает их образы из `BM_BOOTMOD` и снимает
   `RTS_BOOTINHIBIT`, как сейчас.

Каждый шаг заканчивается системой, которая собирается и загружается. Шаги М
вписаны в общий план модернизации (`docs/modernization.md`, «План выполнения»):
М1 = А1, М2 = А2, М3 = А3, М4 = А7, М5 = В1, М6 = В3, М7 = п. 8. Проверка:
М1–М4 — на **i386** (`docs/docker-build.md`), М5–М6 — на **Orange Pi PC Plus**
(QEMU `orangepi-pc` и плата). Тесты — `minix/tests` и `SANITYCHECKS` VM.

| Шаг | Содержание | Проверка |
|---|---|---|
| **М1** | Схема типов памяти (`docs/types-audit.md` §9а) в ядре, VM, libsys и на их границах; `refcount` → `uint32_t` (часть п. 7); места — `docs/types-audit.md`, шаг «А1» | сборка, регрессионные тесты, p64 `scan64.py` |
| **М2** | bootmem в ядре вместо `add_memmap` / `cut_memmap` / `pg_alloc_page`; `kinfo` передаёт `bm_map`; VM читает новую карту (аллокатор пока старый) | тесты bootmem на хосте; загрузка i386 |
| **М3** | buddy (`physmem.c`) вместо битовой карты за интерфейсом `alloc_mem` / `free_mem` | тесты buddy на хосте против эталона; `SANITYCHECKS`; загрузка, тесты |
| **М4** | Ядро: `kas`, арена, пул таблиц, `VMCTL_AS_*`; транслятор i386 (код формата PTE переносится из `vm/pagetable.c` в `kernel/arch/i386/pt.c`); VM переводится на журнал; `vm/arch/` удаляется | загрузка i386, регрессионные тесты, стресс `fork` / `mmap` / `munmap` |
| **М5** | Транслятор earm (ARMv7 short-descriptor, TTBR0/TTBR1) | QEMU `orangepi-pc`, Orange Pi PC Plus |
| **М6** | ASID (п. 5) поверх `kas` | тесты + счётчики сбросов TLB |
| **М7** | Разделяемое АП для LWP (п. 8) | тесты libpthread |

Шаги М1–М3 не зависят от SMP и `kmutex`, их можно делать сразу. М4 требует
`kmutex` (п. 2). SMP на М4 не обязателен: пока у ядра один CPU, сброс TLB
локальный.

| Вариант | Почему отвергнут |
|---|---|
| **Общая структура «список диапазонов» на всё АП, которую ядро целиком перестраивает в аппаратные таблицы при изменении версии** (тупиковая ветка) | полная перестройка O(размер АП) на каждое изменение; указатели в общей памяти работают только при одинаковых адресах у ядра и VM; ядро выделяло память из общего пула и конкурировало с VM |
| **Единая регионная карта физической памяти на всё время работы** (`mmap_utils` тупиковой ветки) | регионная гранулярность вместо постраничной; COW требует счётчика на страницу; указатели на записи устаревают при склейке; RAM смешана с MMIO |
| **VM пишет аппаратные таблицы сам** (MINIX 3 сейчас) | архитектурный код в VM, каждый порт затрагивает VM |
| **Kernel call на каждую операцию отображения** | ловушка на каждую страницу; журнал даёт пакетирование при той же простоте |

Что взято из тупиковой ветки:
- словарь флагов и типов кэширования (исправлен: без совпадающих битов);
- идея версии/номера для ленивого применения (стала `head_seq` / `applied_seq`);
- правило «ядро только `trylock`» и `force_unlock` для упавшего сервера;
- единая структура загрузочной информации вместо разрозненных полей
  (стала `bm_map` в `kinfo`);
- генерации ASID (п. 5).

Практические уроки:
- выходные параметры — только через `T **` или возвращаемое значение, одна
  конвенция кодов возврата;
- общий код ядра и VM — одна библиотека или один заголовок ABI, а не копии файлов;
- каждый уровень сначала проверяется тестами на хосте, затем в системе;
- не удалять старый механизм, пока новый не загрузил систему.

## 10. Открытые вопросы

1. Размер журнала: одной страницы (126 операций) хватит для типичного `fork`
   или `exec`? Если нет — несколько страниц на АП или крупные операции
   (`npages` > 1 уже поддерживается).
2. Переносить ли `refcount` в `vm_page` и упрощать `phys_block` (§4.5) — после
   измерений на М3–М4.
3. Заменять ли `physblocks[]` разреженной структурой — по измерениям расхода
   памяти VM на больших АП.
4. Нужна ли на 32-битных платформах линейная «нижняя память» ядра вместо окон
   (§6.5) — только если окна окажутся узким местом.
5. Live update и перезапуск VM: порядок `VMCTL_AS_RESET` и повторного
   воспроизведения, перенос `as_id` в состояние нового VM.
6. Нужны ли гигантские страницы (`PM_MAX_ORDER` > 10) на встраиваемых целях.
7. ~~**Типы физических адресов**~~ — **решено 2026-10-07** (`docs/types-audit.md`
   §9а): `phys_addr_t` шириной платформы, 64 бита при `CONFIG_PHYS_ADDR_64`
   (PAE/LPAE); номер страницы — `pfn_t`; адрес для устройства — `dma_addr_t` через
   `phys_to_dma()`; длины — `size_t`. В общих структурах ядра и VM (bootmem, журнал
   АПТ, `kinfo`) — фиксированная ширина. Минимальный x86 — Pentium M без
   гарантированного PAE, поэтому PAE на i386 — опция после М4.
