# Docker-окружение для сборки ReMinix

> Описывает `docker/Dockerfile` + `docker/build.mk` — контейнеризованное хостовое
> окружение для `build.sh`/`releasetools/*.sh`, чтобы сборка работала одинаково на
> любой Linux-машине, независимо от того, что установлено на хосте. Не заменяет и не
> изменяет саму систему сборки — см. `docs/build-x86.md`/`docs/build-arm32.md` для
> того, что происходит *внутри* контейнера. Разработано в сентябре 2026 года.
>
> **Статус: готово.** Сборка i386 в этом окружении проверена владельцем проекта на
> реальной машине и работает от начала до конца (тулчейн → мир → release-наборы →
> `minix_x86.img`). Задача по созданию сборочной среды закрыта — см. §7.

## 1. Принцип: обёртка, а не замена

Ключевое наблюдение, на котором строится весь дизайн: `build.sh` уже умеет
самостоятельно собирать **весь** кросс-тулчейн (GCC, LLVM/Clang, binutils, а также
bmake, mtree, pax, makefs и весь остальной инструментарий сборки) из исходников,
которые лежат прямо в дереве, в `tools/` (там же — `gmp`, `mpc`, `mpfr`, нужные для
сборки самого GCC). Это классический подход NetBSD: `build.sh` рассчитан на то, что
запускается на "чужом" хосте (любой Linux, не обязательно NetBSD/MINIX), и сам себе
бутстрапит всё, кроме самого базового набора хостовых инструментов.

Отсюда следствие для архитектуры этого Docker-окружения: **образу не нужно нести
кросс-компилятор или дублировать логику сборки** — только хостовые предпосылки,
которые `build.sh` считает уже существующими (компилятор C/C++, стандартный
POSIX-тулинг) плюс несколько пакетов для вспомогательных шагов (сборка GRUB для
EFI-варианта x86, `git`/`curl` для получения форка U-Boot под ARM). Это делает образ
маленьким и не требующим переделки при добавлении новой целевой архитектуры —
`minix/kernel/arch/amd64/` в будущем появится в дереве, а не в `Dockerfile`.

## 2. Состав образа (`docker/Dockerfile`) и почему именно так

Базовый образ — **Ubuntu 24.04 LTS** (`ubuntu:24.04`): официальный Docker-образ,
долгий цикл поддержки, широкая база пакетов — стандартный выбор для NetBSD-style
кросс-сборки на Linux-хосте.

| Группа пакетов | Зачем |
|---|---|
| `build-essential`, `gawk`, `m4`, `bison`, `flex` | Минимум, который реально нужен `build.sh` на хосте: C/C++ компилятор, которым бутстрапится `tools/make` (нативный `bmake`), и стандартный POSIX-набор, которым дальше собираются `pax`/`mtree`/`makefs`/... Дальше `build.sh` уже сам ведёт себя как "хост с рабочим `cc`". |
| `git`, `curl`, `ca-certificates` | `releasetools/fetch_u-boot.sh` клонирует форк U-Boot MINIX3 (`git://git.minix3.org/u-boot`) на фиксированный коммит; `fetch_and_build_grub` (в `x86_hdimage.sh`) тянет исходники GRUB. Оба шага требуют сети *во время сборки* — это нормально на реальной машине с обычным интернетом. |
| `xz-utils`, `bzip2`, `unzip`, `rsync` | Распаковка/перекладывание исходников и наборов (`sets`) в процессе сборки. |
| `perl`, `python3` | `releasetools/sort_set.pl`; сборочные скрипты GRUB используют python. |
| `autoconf`, `automake`, `pkg-config`, `gettext`, `texinfo` | Нужны только для EFI-варианта x86 (`fetch_and_build_grub` реально собирает GRUB из исходников — это отдельный autotools-проект, не часть дерева ReMinix). |
| `zlib1g-dev`, `libssl-dev` | Линкуются в бутстрапящиеся хостовые `binutils`/`gcc`/`llvm` из `tools/`. |
| `qemu-utils` + библиотеки времени выполнения QEMU (`libglib2.0-0t64`, `libpixman-1-0`, `libfdt1`, `libslirp0`) | `qemu-img` из пакета; сами эмуляторы — QEMU 11.1.0, собранный в стадии `qemu-builder` (§2.2). |
| `sudo`, `less`, `vim-tiny`, `locales` | Удобства для интерактивной работы (`make -C docker -f build.mk shell`), не влияют на сборку. |

Namespace-пакетов из `universe`/`multiverse` (в первую очередь `qemu-system-*`) нет в
дефолтном `sources.list` официального `ubuntu:24.04` — поэтому первый `RUN` в
`Dockerfile` перезаписывает `sources.list`, включая `universe`/`multiverse`.

Образ не содержит `COPY` исходников внутрь себя — дерево ReMinix монтируется как том
при запуске контейнера (см. §3). Поэтому пересборка образа (`make -C docker -f build.mk image`)
занимает секунды/минуты (это просто `apt-get install`), а не пересборку тулчейна — за
одним исключением, см. §2.1.

### 2.1 Отдельная стадия: gcc-7 для хостовых частей сборки (`HOST_CC`/`HOST_CXX`)

`build.sh` бутстрапит свою копию `nbmake` (`usr.bin/make` — древние исходники bmake
из NetBSD) компилятором, который назван в `$HOST_CC` (по умолчанию `cc`) — это
единственное место во всём `build.sh`, где вообще используется `HOST_CC`/
`HOST_CFLAGS`/`HOST_CPPFLAGS`/`HOST_LDFLAGS` (функция `rebuildmake()`). Реальный
кросс-тулчейн (`tools/gcc`, `tools/llvm*`) собирается отдельно и от `HOST_CC` не
зависит.

Проверено на практике (многократные сборки этого дерева на реальном железе):
современный хостовый gcc (Ubuntu 24.04 ставит gcc-13 по умолчанию) не может собрать
`nbmake` — вероятнее всего потому, что начиная с gcc 10 дефолт сменился с `-fcommon`
на `-fno-common`, а старый bmake в стиле K&R, полагающийся на "tentative"
определения одной и той же глобальной переменной в нескольких файлах, из-за этого
падает на этапе линковки ("multiple definition"). gcc-7 — последняя ветка до этой
смены дефолта — собирает без проблем.

Тот же класс проблемы всплыл ещё раз на следующем шаге, уже за пределами
`nbmake`: сборка `tools/binutils` (хостовый binutils/`gold`, используемый как
build tool) падала с `error: 'string' in namespace 'std' does not name a type`
в `external/gpl3/binutils/dist/gold/errors.h` — `std::string` используется без
`#include <string>`, полагаясь на неявный транзитивный инклюд, которого
современные заголовки libstdc++ больше не дают (эта чистка транзитивных
инклюдов в стандартной библиотеке — примерно gcc 11). Разбор
`share/mk/bsd.host.mk` + `tools/Makefile.gnuhost` показал: `CONFIGURE_ENV` для
*любого* хостового GNU-пакета из `tools/` (не только `nbmake`) ставит
`CC=${HOST_CC}` **и** `CXX=${HOST_CXX}`; `HOST_CXX` при этом по умолчанию
(`bsd.host.mk`) — просто `c++`, независимо от `HOST_CC`. То есть `HOST_CC`,
выставленный в gcc-7, чинил `CC`, но `CXX` всё равно оставался системным
g++-13 — тем же классом несовместимости "старые GNU-исходники / новый
компилятор", только в другом месте и по другой переменной.

В `ubuntu:24.04` пакета `gcc-7` уже нет (выпилен после 20.04), а тащить готовый
`.deb` из чужого EOL-релиза Ubuntu — риск несовместимости по версиям glibc с
остальным образом. Поэтому `docker/Dockerfile` собирает gcc-7.5.0 (языки `c,c++`)
из официальных исходников GNU (`ftp.gnu.org`) в отдельной стадии (`FROM ... AS
gcc7-builder`, `--disable-bootstrap` — однопроходная сборка, gcc-7 тут нужен
только как инструмент, а не как продакшн-компилятор, `--program-suffix=-7` —
иначе `make install` кладёт бинарники просто как `gcc`/`g++`, без суффикса) и
копирует готовый `/opt/gcc-7` в финальный образ. Первая сборка образа из-за
этого ощутимо дольше (лишние 15-25 минут на нескольких ядрах), но Docker
кеширует слой, и дальше пересборки образа проходят быстро как раньше;
воспроизводимость не зависит от того, доживёт ли какое-нибудь
old-releases-зеркало или PPA до следующего раза, когда придётся пересобрать
образ с нуля.

В финальном образе gcc-7/g++-7 доступны по абсолютным путям
`/opt/gcc-7/bin/gcc-7` и `/opt/gcc-7/bin/g++-7` (и добавлены в `PATH`, но **в
конец**, не в начало — чтобы `cc`/`gcc`/`c++` по умолчанию везде оставались
текущим gcc-13, кроме двух переменных ниже), и `Dockerfile` выставляет
`ENV HOST_CC=/opt/gcc-7/bin/gcc-7` и `ENV HOST_CXX=/opt/gcc-7/bin/g++-7` — ровно
те переменные, которые читают `rebuildmake()` и `Makefile.gnuhost` для каждого
хостового инструмента из `tools/`. Голые `CC`/`CXX` при этом не трогаются, чтобы
не задеть остальные шаги (в первую очередь — сборку GRUB, у которой
`./configure` сам ищет `CC` в окружении).

### 2.2 Отдельная стадия: QEMU 11.1.0 из исходников (`qemu-builder`)

В Ubuntu 24.04 — QEMU 8.2; проекту нужен актуальный выпуск (`-M orangepi-pc`,
свежий i386/x86_64), версия фиксируется (`ARG QEMU_VERSION`, таблица версий —
`docs/devicetree.md` §1). Стадия `qemu-builder` качает
`https://download.qemu.org/qemu-<версия>.tar.xz`, собирает только нужные цели
(`i386-softmmu`, `x86_64-softmmu`, `arm-softmmu`, `aarch64-softmmu`; riscv64/mips64
добавить при начале этих портов) с `--enable-kvm --enable-slirp`, без
документации, в `/opt/qemu`. Финальный образ копирует `/opt/qemu`, ставит его
первым в `PATH` и при сборке проверяет `qemu-system-i386 --version` (падение
здесь означает нехватку библиотеки времени выполнения). Первая сборка образа —
плюс 10–20 минут, дальше слой кэшируется.

## 3. Где живёт состояние сборки

`build.sh`/`releasetools/*.sh` тратят часы на первую сборку тулчейна и мира — если
каждый запуск контейнера начинать с чистого листа, окружением невозможно будет
пользоваться. Поэтому:

- В контейнер монтируется **только сама директория репозитория** (`-v
  <repo>:/work/reminix`), без родительских каталогов хоста — минимальный периметр
  доступа.
- `OBJ`/`DESTDIR`/`RELEASEDIR` указывают **внутрь** этого тома —
  `/work/reminix/obj/<ARCH>/...` — а не наружу, в отличие от голого запуска
  `releasetools/*.sh` на хосте, где по умолчанию используется `../obj.<ARCH>` (сосед
  каталога репозитория, см. `docs/build-x86.md` §2, `docs/build-arm32.md` §2). Это
  сознательное отступление от дефолта скриптов, а не расхождение с ними: сами
  скрипты объявляют `OBJ`/`DESTDIR`/`RELEASEDIR` через `: ${VAR=default}`, то есть
  честно уважают переменные окружения, если те уже заданы — `docker/build.mk`
  экспортирует их явно (см. §4), и скрипты просто используют переданное значение.
- `obj` (без слэша, без расширения) уже присутствует в корневом `.gitignore` как
  паттерн, действующий на любой глубине — так что `obj/i386`, `obj/evbearm-el` и
  т.д. автоматически не попадают в git, ничего дополнительно настраивать не нужно.
- **Кросс-тулчейн — в `obj/<ARCH>[-smp]/tooldir`** (`build.sh -T`, а для
  `releasetools` — `CROSS_TOOLS`). По умолчанию `build.sh` называет каталог
  `tooldir.<uname -s>-<uname -r>-<uname -m>`, то есть по версии ядра хоста, и после
  каждого обновления ядра Ubuntu собирал тулчейн заново. При смене `TOOLDIR` у
  существующего `OBJ` удалить `$OBJ/tools`: иначе `build.sh -u` сочтёт
  инструменты установленными и новый каталог останется неполным
  (`don't know how to make …/tooldir/bin/nbfile`).
- **SMP-вариант** (`SMP=yes`): `-V CONFIG_SMP=y -V CONFIG_MAX_CPUS=8` попадают в
  `CPPFLAGS` всего дерева (`share/mk/bsd.own.mk`), поэтому отдельный `obj/i386-smp`
  со своим тулчейном и образ `minix_x86_smp.img`.
- Из этого следует практическое правило: разные `ARCH` не пересекаются
  (`obj/i386` и `obj/evbearm-el` — разные деревья), а `make -C docker -f build.mk clean-obj
  ARCH=<arch>` даёt чистую пересборку конкретной архитектуры без пересборки
  остальных.

## 4. Как пользоваться

Всё — через `docker/build.mk`, запускается из корня репозитория:

Полный список целей и параметров с описанием — `make -C docker -f build.mk help`
(цель по умолчанию, Docker не запускает; справка — строки `#>` в начале
`build.mk`, её обновляют вместе с любым изменением целей и параметров).

```sh
make -C docker -f build.mk help                     # справка: цели, параметры, примеры
make -C docker -f build.mk image                    # собрать образ окружения (один раз, дальше кэшируется)
make -C docker -f build.mk shell                    # интерактивная оболочка внутри контейнера, ARCH=i386 по умолчанию
make -C docker -f build.mk shell ARCH=evbearm-el    # то же, под ARM

make -C docker -f build.mk build ARCH=amd64 BUILD_TARGET=tools   # прямой вызов build.sh -m amd64 ... tools
make -C docker -f build.mk build BUILD_TARGET=release            # эквивалент "make -C docker -f build.mk build" (release — дефолт)

make -C docker -f build.mk hdimage                  # releasetools/x86_hdimage.sh → obj/i386/.../minix_x86.img
make -C docker -f build.mk sdimage                  # releasetools/arm_sdimage.sh → minix_arm_sd.img (BeagleBoard-xM)

make -C docker -f build.mk hdimage SMP=yes          # то же с CONFIG_SMP -> minix_x86_smp.img
make -C docker -f build.mk test-i386                # автоматический прогон minix/tests (docs/testing.md §1)
make -C docker -f build.mk test-i386 SMP=yes CPUS=4 TESTS=43,71
make -C docker -f build.mk test-snapshot            # из другого терминала: снимок идущего прогона
make -C docker -f build.mk test-stop                # из другого терминала: post-mortem и остановка (как Ctrl-C)
make -C docker -f build.mk run-i386 SMP=yes CPUS=4  # интерактивная консоль MINIX с журналом и снимками (docs/testing.md §1в)
make -C docker -f build.mk qemu-hdimage             # qemu-system-i386 -hda minix_x86.img (KVM, если /dev/kvm доступен)
make -C docker -f build.mk qemu-sdimage             # qemu-system-arm -M beaglexm ...

make -C docker -f build.mk clean-obj ARCH=i386      # снести obj/i386 (например, после смены BUILDVARS)
make -C docker -f build.mk clean-image              # удалить сам docker-образ
```

`JOBS` (по умолчанию — `nproc` хоста), `BUILDVARS` (доп. флаги `-V var=val` для
`build.sh`, см. пример с `MKGCCCMDS`/`MKLLVM` для ARM в `docs/build-arm32.md` §2) и
`IMAGE_TAG` — тоже переопределяемые переменные `make`.

Каждая цель, кроме `help` и `clean-*`, сама пересобирает образ при необходимости (`image` —
это зависимость; шаг ходит в сеть за базовым образом — без сети `make -o image …`), так что отдельно помнить про `make -C docker -f build.mk image` не обязательно
— но при первом запуске это удобно сделать явно, чтобы увидеть вывод `apt-get`
отдельно от вывода сборки.

`hdimage`/`sdimage`/`qemu-*` жёстко фиксируют `ARCH` (i386 и evbearm-el
соответственно) — это те же архитектуры, для которых жёстко написаны сами
`releasetools/x86_hdimage.sh`/`arm_sdimage.sh` (см. `docs/build-x86.md`,
`docs/build-arm32.md`); общая цель `build` принимает любой `ARCH`, в том числе ещё не
портированный (`amd64` и т.д.) — она просто дойдёт до места, где дерево спотыкается
об отсутствующий `minix/kernel/arch/<arch>/`, и это само по себе полезный дымовой
тест прогресса конкретного порта.

## 5. Добавление новой архитектуры

Ничего в `docker/` не привязано к конкретному списку архитектур, кроме
удобных ярлыков `hdimage`/`sdimage`/`qemu-*`. Когда появится, например,
`minix/kernel/arch/amd64/` (см. `docs/porting.md`):

- `make -C docker -f build.mk build ARCH=amd64` уже работает без изменений в `docker/`.
- Свой `releasetools/amd64_*image.sh` (по аналогии с `x86_*image.sh`) можно так же
  обернуть новой целью в `docker/build.mk` по образцу `hdimage`, если появится
  постоянная необходимость.
- В `Dockerfile` менять, скорее всего, ничего не придётся — `qemu-system-x86` уже
  умеет `qemu-system-x86_64`.

## 6. Многопользовательские машины / права доступа

`Dockerfile` создаёт непривилегированного пользователя `builder` с UID/GID,
переданными как build-args; `docker/build.mk` сам подставляет туда `id -u`/`id -g`
хоста при сборке образа. Файлы, которые появляются в примонтированном дереве
(`obj/`, собранные образы дисков), оказываются владением того же пользователя, что
запустил `make`, а не `root` — стандартная практика для dev-контейнеров с
bind-mount'ами. На машине с несколькими разработчиками это означает, что у каждого,
строго говоря, должен быть свой локальный образ (или общий с UID, под которым все
согласны работать) — для одиночного форка/машины это не проблема.

## 7. Статус проверки

**Сборочная среда готова, задача закрыта.** Владелец проекта проверил сборку i386
через это окружение на реальной машине: `make -C docker -f build.mk hdimage`
проходит от начала до конца (кросс-тулчейн из `tools/`, мир, release-наборы,
упаковка `minix_x86.img`).

Окружение изначально писалось по чтению `build.sh`, `tools/` и
`docs/build-*.md`, без запуска. Реальные прогоны вскрыли ряд проблем; все они
исправлены в `docker/Dockerfile`/`docker/build.mk`, сама система сборки
(`build.sh`, `releasetools/*`) не менялась:

| Проблема | Исправление |
|---|---|
| `docker/Makefile` отклонялся файловым мостом как protected file | переименован в `docker/build.mk`, вызов `make -C docker -f build.mk ...` |
| `useradd: UID 1000 is not unique` (в `ubuntu:24.04` уже есть пользователь `ubuntu`) | удаление существующих пользователя/группы с целевыми UID/GID перед созданием `builder` |
| флаги `docker run` (`--device`, `-it`) подставлялись после имени образа | `DOCKER_RUN_BASE` (флаги) + `$(IMAGE)` отдельно |
| лишний `ENTRYPOINT ["/bin/bash"]` ломал `bash -lc '...'` | убран |
| `nbmake` не собирается современным gcc | стадия `gcc7-builder`, `HOST_CC=/opt/gcc-7/bin/gcc-7` (+ `--program-suffix=-7`), см. §2.1 |
| `tools/binutils` (`gold`): `'string' in namespace 'std'` | `HOST_CXX=/opt/gcc-7/bin/g++-7`, см. §2.1 |
| `x86_hdimage.sh` не находил `sets` (задвоенный суффикс `RELEASEDIR`) | `RELEASEDIR=${OBJ}/releasedir` без `/<arch>/binary`, см. `docs/build-x86.md` §3 |
| `qemu-hdimage`: нет прав на `/dev/kvm` | `--group-add` с GID группы `kvm` хоста, явный `format=raw` |
| `download_prerequisites` gcc-7 висит на `ftp://gcc.gnu.org` | замена на `https://` в стадии `gcc7-builder` |
| тулчейн пересобирался после обновления ядра хоста | фиксированный `TOOLDIR=$OBJ/tooldir` |

Два пункта из этой таблицы — свойства самой системы сборки, а не обёртки, и
актуальны при запуске `build.sh`/`releasetools/*.sh` на голом хосте без Docker:
`HOST_CXX` нужно задавать вместе с `HOST_CC` (старый GNU-код в `tools/`), а
`RELEASEDIR`, если задаётся, должен быть без суффикса `/<arch>/binary`.

Отдельно не прогонялись (в рамки закрытой задачи не входят, проверяются по мере
надобности): `qemu-hdimage` после фикса прав KVM и ARM-путь
(`sdimage`/`qemu-sdimage`, BeagleBoard-xM). Если при первом прогоне ARM-пути
что-то всплывёт — дополнить таблицу выше.
