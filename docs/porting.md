# ReMinix — план портирования на новые архитектуры

> Долгоживущий документ-решение. Обновляйте при изменении самого плана/подхода, а не
> при продвижении по конкретным задачам — прогресс отражайте в `docs/handoff.md` и/или
> отдельным трекером задач.

## Цель

Портировать ReMinix (форк MINIX 3, зафиксирован на базе синхронизации с NetBSD-8,
последний апстрим-коммит 2018-11-04) на:

1. **amd64** (x86-64)
2. **arm32** (обобщённый ARMv7/v8-32, не только текущий OMAP-BSP)
3. **aarch64** (ARMv8 64-бит)
4. **risc-v64**
5. **mips64**

Итоговая цель — микроядерная ОС для встраиваемых систем, а не десктоп/сервер общего
назначения, так что при прочих равных приоритет — компактность, предсказуемость и
изоляция отказов, а не полнота POSIX/производительность.

## Точка отсчёта: что уже поддерживается

См. `docs/architecture.md`, §7. Коротко: полноценно работает **i386**, частично —
**earm** (ARMv7, только BSP для TI OMAP). Обе архитектуры продублированы в трёх местах:

1. `minix/kernel/arch/<arch>/` — машинно-зависимое ядро.
2. `minix/servers/vm/arch/<arch>/` — формат таблиц страниц для VM-сервера.
3. `sys/arch/<arch>/` (унаследовано из NetBSD) — заголовки/низкоуровневый код,
   используемый и ядром, и юзерлендом.

Плюс кросс-тулчейн в `tools/` (там уже есть LLVM/Clang, не только GCC) и генерация
загрузочных образов в `releasetools/` (сейчас — только `x86_*image.sh` и
`arm_sdimage.sh` c U-Boot).

**Существующая пара i386/earm — лучший референс**: она буквально показывает, какие
файлы и директории нужно продублировать/создать для добавления архитектуры в это
конкретное дерево, в отличие от портирования "с нуля" по книге Таненбаума.

## Общий чек-лист добавления новой архитектуры `<arch>`

Из анализа структуры (без ещё детального чтения кода — это следующий шаг):

1. **Ядро**: создать `minix/kernel/arch/<arch>/` — как минимум аналоги файлов, что
   есть у i386/earm: `head.S`/`exc.S` (точка входа/обработка исключений), `klib.S`
   (низкоуровневые примитивы: свитч контекста, atomic-операции), `memory.c` (карта
   памяти, инициализация MMU), `pg_utils.c`/`protect.c` (управление таблицами страниц
   и защитой), `arch_clock.c` (таймер), `arch_system.c` (реализация arch-specific
   kernel calls), `interrupt.c`/`hw_intr.c` (контроллер прерываний — APIC у i386,
   аналог у earm), `pre_init.c` (ранняя инициализация до включения MMU),
   `procoffsets.cf` + `usermapped_*` (ABI-смещения полей структур, используемые
   ассемблерными вставками), `kernel.lds` (linker script), `include/arch_proto.h`,
   `include/archconst.h`, `include/cpufunc.h` и т.п. — платформенные заголовки.
2. **VM-сервер**: `minix/servers/vm/arch/<arch>/pagetable.h` + `Makefile.inc` —
   формат и операции над таблицами страниц конкретной архитектуры со стороны
   пользовательского VM-сервера (он не работает напрямую с MMU, но должен понимать
   формат PTE/PDE, чтобы строить адресные пространства процессов).
3. **Заголовки NetBSD** (`sys/arch/<arch>/`): либо импортировать соответствующий порт
   из апстрима NetBSD (ближайшая по времени/API версия к NetBSD-8, уже используемой в
   дереве), либо писать заголовки вручную по образцу i386/arm — для amd64/aarch64/
   riscv64/mips64 разумнее **импортировать**, т.к. объём заголовков (регистры,
   структуры контекста, PCI/ACPI-глюки и т.д.) большой и хорошо покрыт апстримом.
4. **Тулчейн** (`tools/`): убедиться, что LLVM/Clang и `binutils`/`gcc` в дереве
   поддерживают целевой triple (`<arch>-elf-minix` или аналог по образцу
   `i586-elf32-minix-`/`arm-elf32-minix-` — это реальные префиксы, используемые в
   `releasetools/{x86,arm_sd}image.sh`, см. `docs/build-x86.md` §2 и
   `docs/build-arm32.md` §2). Возможно, потребуется актуализация версий
   LLVM/binutils, если целевая архитектура (особенно RISC-V) слабо поддерживалась
   версией тулчейна 2018 года.
   **Важное наблюдение** (подтверждено чтением `build.sh`): таблица
   `valid_MACHINE_ARCH` внутри `build.sh` — это **немодифицированная таблица
   NetBSD** и уже содержит `MACHINE=amd64 MACHINE_ARCH=x86_64` и
   `MACHINE=evbarm64 MACHINE_ARCH=aarch64` (как и riscv/mips записи). То есть сам
   `build.sh` не откажет в `-m amd64`/`-m evbarm64` — он вообще не содержит
   MINIX-специфичных ограничений по архитектурам (`grep __MINIX build.sh` —
   пусто). Реальный блокер везде один и тот же: отсутствие
   `minix/kernel/arch/<arch>/`, `minix/servers/vm/arch/<arch>/` и остального,
   перечисленного в этом чек-листе. Это усиливает выбор amd64 как первого шага
   (см. «Предлагаемая последовательность» ниже) — на уровне `build.sh` для него
   вообще ничего не нужно менять.
   Также замечено: сборка под `earm` по умолчанию идёт через GCC
   (`-V MKGCCCMDS=yes -V MKLLVM=no` в `arm_sdimage.sh`), а не LLVM/Clang, вопреки
   тому, что можно было бы предположить по наличию `minix/llvm/` в дереве — сборка
   с LLVM для ARM существовала как закомментированный альтернативный набор флагов,
   но не была путём по умолчанию. Это стоит уточнить/перепроверить при выборе
   тулчейна для новых архитектур.
5. **`share/mk`**: bmake-инфраструктура читает `MACHINE`/`MACHINE_ARCH` — нужно
   завести новую пару значений и прописать её в соответствующих `bsd.*.mk`/
   `Makefile.inc` по образцу существующих.
6. **Загрузка/образы**: свой bootloader-путь.
   - amd64: скорее всего расширение существующего BIOS-пути `x86_hdimage.sh` плюс,
     желательно, UEFI-путь (отдельная задача).
   - arm32/aarch64: U-Boot по аналогии с `arm_sdimage.sh`/`fetch_u-boot.sh`, но без
     привязки к TI OMAP; для aarch64 — часто ещё и EFI (большинство SBC на ARM64
     грузятся через U-Boot+EFI или напрямую через собственный firmware).
   - riscv64: OpenSBI + U-Boot/EFI (стандартный путь в экосистеме RISC-V) либо прямой
     запуск ядра из SBI.
   - mips64: сильно зависит от целевой платформы (часто — своя PROM/U-Boot; единого
     стандарта в духе ARM/RISC-V нет), нужно фиксировать конкретную референсную плату
     до начала работы.
7. **Драйверы**: ядро+VM не требуют драйверов устройств для загрузки в консоль, но
   реальная встраиваемая система требует минимум: консольный UART (`drivers/tty`),
   таймер/RTC (`drivers/clock`), блочное устройство или сетевая загрузка
   (`drivers/storage`, `drivers/net`) для полноценной многопользовательской загрузки.
   Для новых плат под arm32/aarch64/riscv64/mips64 это, как правило, новый BSP по
   аналогии с `earm/bsp/ti/*`, а не изменение общего кода.
8. **Тесты дымового прогона**: под QEMU (`qemu-system-x86_64`, `qemu-system-arm`/
   `qemu-system-aarch64`, `qemu-system-riscv64`, `qemu-system-mips64`) — самый дешёвый
   способ итеративно отлаживать порт до появления реального железа.

## Предлагаемая последовательность архитектур

Порядок продиктован объёмом необходимых изменений "с нуля" и близостью к уже
работающему коду:

1. **amd64** — ближе всего к уже полностью работающему i386 (тот же x86, тот же APIC/
   ACPI, тот же стиль тулчейна), самая низкая планка входа. Хороший способ также
   выявить места в машинно-независимом коде ядра/серверов, где сейчас неявно
   предполагается 32-битный указатель/regsize (то есть эта работа параллельно
   "обеляет" остальной код перед более экзотическими портами).
2. **arm32 (обобщение earm)** — прежде чем добавлять aarch64, стоит решить, что делать
   с существующим OMAP-only `earm`: либо явно зафиксировать его как "earm/ti" и
   развести общий ARMv7 слой (по образцу `sys/arch/arm` + `evbarm` в NetBSD, где как
   раз есть разделение "общий ARM" / "конкретная evb-плата"), либо принять решение не
   инвестировать в generic arm32 и сразу переходить к aarch64 на новой, более
   актуальной платформе. Это решение стоит явно зафиксировать здесь после анализа.
3. **aarch64** — самая практически востребованная архитектура для современных
   встраиваемых применений (Raspberry Pi 3/4/5, множество SBC). Возможный референс
   для BSP — Raspberry Pi (`evbarm`/`raspberrypi` в NetBSD).
4. **risc-v64** — новая архитектура для проекта, но с хорошей поддержкой в LLVM и
   заголовках NetBSD более новых версий (нужно будет тащить их из апстрима отдельно
   от базовой NetBSD-8, т.к. поддержка RISC-V в NetBSD появилась позже 2018 года).
5. **mips64** — наименее приоритетна: разнородная экосистема плат/загрузчиков,
   меньше готовых референсов в актуальном апстриме NetBSD по сравнению с riscv64.

Этот порядок — первичная гипотеза по итогам изучения кода, а не окончательное решение;
стоит пересмотреть после того, как появится ясность по конкретному "железу", на
котором планируется тестировать каждый порт.

## Дополнено по итогам разбора `releasetools/` (см. `docs/build-x86.md`, `docs/build-arm32.md`)

- Текущий ARM-порт (`earm`) — это не общий ARMv7, а порт под **один вендорский BSP**
  (TI OMAP3/AM335x, BeagleBoard/BeagleBone), это видно на трёх уровнях сразу:
  `minix/kernel/arch/earm/bsp/ti/*`, жёстко заданные адреса загрузки в
  `releasetools/gen_uEnv.txt.sh`, и список плат в `arm_sdimage.sh`. Пункт плана
  «arm32 (обобщение earm)» — это в первую очередь разведение общего ARMv7-кода и
  BSP-специфики по образцу NetBSD `sys/arch/arm` (общее) / `sys/arch/evbarm`
  (платы), а не косметика.
- ARM-загрузка идёт через **форк U-Boot, поддерживаемый самим MINIX3**
  (`git://git.minix3.org/u-boot`, ветка `minix`, зафиксирован конкретный коммит) —
  это отдельный проект вне основного дерева, собираемый отдельно. Для aarch64/
  riscv64 нужно решить: расширять этот форк новыми платами, или переходить на
  апстримный U-Boot (у которого поддержка новых архитектур и так активно
  развивается).
- UEFI-загрузка (через GRUB) в текущем дереве реализована **только для i386**
  (`releasetools/x86_hdimage.sh`, функция `fetch_and_build_grub`) и нигде больше —
  если для amd64/aarch64 тоже нужен UEFI-путь, его придётся строить по аналогии, а
  не переиспользовать как есть.
- `build.sh` использует **немодифицированную таблицу архитектур NetBSD**
  (`valid_MACHINE_ARCH`) без каких-либо `__MINIX`-ограничений — `amd64` и
  `evbarm64`/`aarch64` уже в этой таблице. Блокер для новых архитектур — это
  исключительно отсутствующий MINIX-специфичный код (`minix/kernel/arch/<arch>` и
  т.д.), а не сам скрипт сборки.

## Открытые вопросы (требуют решения до/во время работы)

- Какая конкретная плата/SoC — цель для каждой архитектуры (влияет на выбор BSP,
  загрузчика, набора драйверов)? Например, для aarch64 — Raspberry Pi конкретной
  ревизии, QEMU virt-машина, или что-то ещё.
- Остаёмся ли на базе NetBSD-8 (замороженной в 2018) для новых архитектур, или для
  импорта заголовков/кода под riscv64/aarch64 разумнее подтянуть более новый срез
  NetBSD (учитывая, что и riscv, и полноценный arm64 у NetBSD появились/созрели уже
  после 2018 года)? Второе технически сложнее (расхождение версий), но избавляет от
  необходимости писать с нуля то, что уже есть в апстриме.
- Нужно ли сохранять полную POSIX-совместимость унаследованного userland на всех
  новых архитектурах, или для встраиваемого применения допустим урезанный набор
  (меньше `usr.bin`/`games`/X11 и т.п.)?
- Приоритет между "довести earm до generic arm32" и "сразу перейти к aarch64" (см.
  выше) — нужно явное решение, а не default по инерции.
