# ReMinix — тестирование: прогон, точка отсчёта, найденные ошибки

> Долгоживущий документ. Как запускать регрессионные тесты `minix/tests`, эталонные
> результаты (точка отсчёта), метрики «тяжёлых» тестов и найденные при прогонах
> ошибки. Обновляйте при изменении процедуры, после новой точки отсчёта и при
> обнаружении ошибок. Критерий «тесты прошли» — `docs/modernization.md`, раздел
> «Рабочий процесс и общие решения».

## 1. Автоматический прогон (основной способ)

```sh
make -C docker -f build.mk hdimage                       # образ (rc.d/minixtests внутри)
make -C docker -f build.mk test-i386                     # все тесты, 1 CPU
make -C docker -f build.mk test-i386 TESTS=1,2,43        # выбранные
make -C docker -f build.mk hdimage SMP=yes               # SMP-сборка (obj/i386-smp)
make -C docker -f build.mk test-i386 SMP=yes CPUS=4      # прогон на 4 CPU
make -C docker -f build.mk test-i386 SMP=yes CPUS=4 KARGS=no_apic=1  # SMP-ядро на 1 CPU
```

SMP: ядро по умолчанию грузится с `no_apic=1`, и SMP-ядро уходит в
однопроцессорный режим на 8259 (`smp_single_cpu_fallback`, BKL при этом
работает). Поэтому при `CPUS>1` `run-tests.sh` сам добавляет `no_apic=0`;
`KARGS` — дополнительные аргументы ядра (свой `no_apic=` в `KARGS` отменяет
автоматический). Настоящий SMP узнаётся по строкам `CPU N is up` в журнале.
В режиме APIC `ramdisk/rc` запускает сервис `acpi` (без него `pci` падает:
«Cannot use APIC mode without ACPI»).

Прочие переменные `test-i386` (все — в `docker/build.mk`):
- `HANG_IDLE=N` — секунды тишины на консоли до признания зависания (§1б);
- `SNAPSHOT_AT=N` — через N **реальных** секунд снять снимок работающей системы
  (как post-mortem, машина продолжает работу) в `<журнал>.snapshot-<N>s/`;
- `ACCEL=tcg|kvm` — вместо автоматического выбора (KVM, если доступен). TCG
  помогает отличить ошибку гостя от эффекта KVM;
- `KARGS=tickdebug=N` — каждый CPU печатает строку раз в N своих тиков (сколько
  тиков, сколько из них не IDLE, текущий процесс). **Глушит сторож тишины**: при
  зависании дампа не будет.

Как устроено (`docker/run-tests.sh`, `etc/rc.d/minixtests`):
- QEMU 11.1 (из Docker-образа) грузит ядро и модули из
  `obj/<arch>/destdir.i386/boot/minix/.temp` напрямую (`-kernel`/`-initrd`,
  multiboot), без меню загрузчика; корневая ФС — из `minix_x86[_smp].img`,
  открытого с `snapshot=on` (образ не меняется); DMA включён; консоль на
  последовательный порт;
- командная строка ядра `testrun=1 [testlist=43,71]` включает
  `rc.d/minixtests`. Скрипт выполняется **синхронно, последним в rc**
  (`REQUIRE: LOGIN inetd local`): пока rc не закончился, init не запускает getty,
  а getty делает `revoke` консоли — вывод фонового процесса пропадал бы. Пауза
  `testdelay` (30 с) перед запуском, затем `run -T`, метки
  `REMINIX-TESTS-BEGIN/END`, 5 с на опустошение очереди TTY, `halt -p`;
- на хосте: таймаут (`TEST_TIMEOUT`, 5400 с), разбор TAP, сверка с
  `docker/tests-known-failures.i386`. Итог: **PASS / FAIL** (новые падения) /
  **HANG** / **CRASH** / **INCOMPLETE** / **INTERRUPTED**; код возврата 0/1/3.
  Журнал — `obj/test-logs/i386[-smp]-cpuN-<дата>.log`, итог дублируется в
  `<журнал>.result` (виден мосту, присылать не нужно).

## 1а. Ручной прогон на i386 (QEMU)

Для отладки и интерактивной работы.

```sh
make -C docker -f build.mk hdimage          # образ minix_x86.img
script -c "qemu-system-i386 -enable-kvm -m 1024 -smp 1 \
  -drive file=minix_x86.img,format=raw,if=ide \
  -serial stdio" ~/reminix-run.log          # журнал всего вывода консоли
```

- Консоль на последовательный порт (иначе журнал не сохранить):
  - пункт меню 4 «ALIX» (`console=tty00 consdev=com0`, **но с `ata_no_dma=1`** —
    диск в режиме PIO, под KVM очень медленно, см. §3);
  - **предпочтительно** — пункт 6 «Drop to boot prompt» и:
    ```
    load_mods /boot/minix_default/mod*
    multiboot /boot/minix_default/kernel rootdevname=c0d0p0 console=tty00 consdev=com0
    ```
    (то же, но с DMA).
- Вход `root` без пароля, затем `cd /usr/tests/minix-posix && ./run`. Только от root
  выполняются `isofs`, `vnd`, `rmib`, `relpol`. Один тест: `./run -t 43`.
- Alt+F1..F4 в окне QEMU перехватывает GNOME — переключать консоли через монитор
  QEMU (Ctrl+Alt+2): `sendkey alt-f2`.

## 1б. Дамп машины: зависание, Ctrl-C, снимок по запросу

Снять состояние машины можно в любой момент прогона:

| Как | Что происходит | Куда |
|---|---|---|
| консоль молчит `HANG_IDLE` с или прогон дольше `TEST_TIMEOUT` | post-mortem, QEMU останавливается, `RESULT: HANG` | `<журнал>.postmortem/` |
| **Ctrl-C** в терминале `test-i386` или `make -C docker -f build.mk test-stop` из другого | post-mortem, QEMU останавливается, `RESULT: INTERRUPTED` | `<журнал>.postmortem/` |
| второй Ctrl-C (или `test-stop`) во время дампа | дамп прерывается, QEMU останавливается сразу | — |
| `make -C docker -f build.mk test-snapshot` из другого терминала | снимок, машина продолжает работу | `<журнал>.snapshot-<N>s/` (N — секунды от старта) |
| `SNAPSHOT_AT=N` | один снимок через N с | то же |

Устройство: `run-tests.sh` — PID 1 контейнера. Ядро не применяет к PID 1
действия сигналов по умолчанию, поэтому раньше Ctrl-C терялся и QEMU оставался
работать в фоне. Теперь скрипт сам обрабатывает SIGINT/SIGTERM (дамп и
остановка) и SIGUSR1 (снимок); цикл ожидания реагирует сразу, без задержки
до 5 с. Контейнер `test-i386` помечен меткой `reminix-test=1`, по ней
`test-snapshot` / `test-stop` находят его и шлют `docker kill -s USR1|TERM`.
`docker stop` для этого не годится: через 10 с он шлёт SIGKILL, и дамп может
не успеть; после `docker kill` без `-s` (SIGKILL) дампа не будет.

Содержимое дампа (одинаково для всех случаев). Через монитор QEMU
`docker/qemu-postmortem.py` останавливает машину и пишет:

`HANG_IDLE` по умолчанию 600 с: в TAP-режиме тест печатает только по
завершении, поэтому значение больше самого долгого теста.

- `monitor.txt` — `info registers`, `info lapic` и стек (`x/64xw $esp`) каждого
  CPU, `info pic`, `info irq`;
- `symbols.txt` (`nm -n -S`) и `kernel` — копия ELF ядра для `objdump -d`;
- `<символ>.bin` — память ядра: `proc`, `priv`, `__cpu_local_vars`, стеки ядра
  (`k_stacks_start`), замки, `kinfo`, `kmess`…;
- `bkl.txt` (только SMP-ядро) — владелец BKL и последние 64 захвата/освобождения
  с местом вызова и функцией уровнем выше. Пишется ядром: `BKL_LOCK/UNLOCK` идут
  через `bkl_lock()/bkl_unlock()` (`minix/kernel/smp.c`); попытка CPU взять уже
  свой BKL отмечается как `RE-LOCK`.

Разбор: адреса из стека и `EIP` — по `symbols.txt`; цепочка кадров — по `%ebp`
(ядро собрано с указателями кадра; входные заглушки обнуляют `%ebp`). Под
`cpuN` с `EIP=000fd0b1`, `CR0=0x11`, `HLT=1` — AP, которые MINIX не запускал
(стоят в SeaBIOS). `EIP` в `hlt` QEMU показывает как адрес следующей команды.

Отладочные данные ядра, которые сохраняет дамп:
- `dbg_cpu_events.bin` — для каждого CPU четыре `u32`: вызовы
  `timer_int_handler`, `context_stop_idle`, IPI планировщика, уходы в `hlt` из
  `idle()` (всегда включено, `minix/kernel/clock.c`);
- `tick_debug_*.bin` (при `tickdebug=N`), `lapic_bus_freq.bin`;
- `dbg_boot_ev.bin` / `dbg_boot_nev.bin` — первые 32 события загрузки AP
  (`arch_clock.c`), по 6 `u32`: метка (1 — AP запускает LAPIC, 2 — BSP
  перевёл LAPIC на виртуальный адрес, 3 — тик на AP), CPU, TSC >> 8, `CR3`,
  `lapic_eoi_addr`, `ISR` векторов 224–255 (§4.11);
  `lapic_addr.bin`, `lapic_eoi_addr.bin`.

- `vga.txt` — текстовый экран VGA (0xb8000, 80×25). **Паника ядра
  печатается только сюда**: ядро пишет прямо в видеопамять, а последовательная
  консоль идёт через TTY, который в этот момент уже не работает (так было с
  §4.15: на serial — тишина, на VGA — `Divide error` со стеком);
- `kmessages.bin` / `kmessages.txt` — буфер сообщений ядра.

Если причины нет и на VGA, ищите её по стеку (`k_stacks_start.bin`: `panic`
← `inkernel_disaster` ← `exception_handler`, рядом номер исключения, код
ошибки и `EIP`/`CS`), `CR2` — в `info registers`.

## 1в. Интерактивный запуск с журналом и снимками (`run-i386`)

```sh
make -C docker -f build.mk run-i386 SMP=yes CPUS=4        # консоль MINIX в этом терминале
make -C docker -f build.mk test-snapshot                   # из другого терминала: снимок
make -C docker -f build.mk test-stop                       # из другого терминала: дамп и остановка
(sleep 90; echo root; sleep 5; echo top) | make -C docker -f build.mk run-i386 SMP=yes CPUS=4
```

Загрузка — как у `test-i386` (`-kernel`/`-initrd`, образ с `snapshot=on`, при
`CPUS>1` — `no_apic=0`), но без `testrun`: система грузится до приглашения
`login` на последовательной консоли (`root` без пароля). Сценарий —
`docker/run-console.sh`:
- консоль — chardev `stdio` с `signal=off`: Ctrl-C уходит в MINIX,
  `Ctrl-A x` — выйти из QEMU сразу (без дампа), `Ctrl-A h` — клавиши QEMU;
- весь вывод консоли пишется в
  `obj/test-logs/i386[-smp]-cpuN-console-<дата>.log`, итог — в `….result`;
- снимки (`test-snapshot`, `SNAPSHOT_AT`) и дамп (`test-stop`) — как в §1б;
- **автоснимок**: на каждую новую строку, совпавшую с `PANIC_RE` (по
  умолчанию `panic`), снимается снимок. Проверяются журнал консоли (паника
  сервера: RS его перезапускает, машина работает дальше) и раз в 10 с экран
  VGA (`docker/qemu-vga.py`): паника ядра печатается только туда, на
  последовательной консоли после неё — тишина (§4.15);
- ввод можно подать конвейером — так воспроизводятся сценарии вроде «войти и
  запустить `top`» без ручной работы.

## 1г. earm: `test-earm`, `run-earm` (каркас)

```sh
make -C docker -f build.mk sdimage   BOARD=<плата>
make -C docker -f build.mk test-earm BOARD=orangepi-pc [CPUS TESTS HANG_IDLE …]
make -C docker -f build.mk run-earm  BOARD=orangepi-pc [CPUS SNAPSHOT_AT PANIC_RE]
```

Те же сценарии, что у i386 (`run-tests.sh`, `run-console.sh` с `TARGET=earm`,
`MACHINE=<машина QEMU>`): журнал `obj/test-logs/earm-<плата>-cpuN-*.log`, итог в
`.result`, снимки и дамп (`test-snapshot`/`test-stop` — общие для всех
архитектур, рассчитаны на один запущенный тестовый контейнер), автоснимок по
`PANIC_RE` на консоли. QEMU — `qemu-system-arm -M <машина>` (TCG) с образом SD
(`if=sd`, `snapshot=on`); символы для дампа — из ELF ядра earm; в дампе нет
x86-частей (LAPIC, PIC, `$esp`, VGA).

Ограничения (2026-10-02):
- машина в апстримном QEMU есть только у `orangepi-pc`; для `beaglexm` и
  `beaglebone` цели сообщают, что машины нет (образы — только для железа,
  `docs/build-arm32.md` §5);
- MINIX на Orange Pi PC пока не грузится (BSP — Б1, загрузка U-Boot + FIT — Б2);
- параметры ядра (`testrun`, `testlist`, `KARGS`) на earm передаёт U-Boot, а не
  multiboot: `test-earm` пока сообщает об этом и завершается, `run-earm`
  игнорирует `KARGS`. Передача появится вместе с загрузкой Б2.

## 1д. Тесты на хосте (`host-test`, `minix/tests/host`)

Модули ReMinix, написанные на чистом C без зависимостей от ядра и серверов
(bootmem, buddy, кодировщик журнала таблиц страниц — `memory.md`; libfdt —
`devicetree.md` 0.6), проверяются на Linux, без образа и QEMU, за секунды.

```sh
make -C docker -f build.mk host-test                          # все модули, все варианты
make -C docker -f build.mk host-test HOST_TESTS=bitmap HOST_VARIANTS=m64-san
make -C minix/tests/host check                                # без Docker (gcc с multilib)
```

- **Модуль** — подкаталог `minix/tests/host/<модуль>/` с программами `t_*.c`.
  Каждая включает `hosttest.h` (в нём и `main()`) и описывает тесты
  `TEST(имя) { ... }`; проверки `CHECK(усл)`, `CHECK_EQ(a, b)` (печатает оба
  значения), `REQUIRE(усл)` (заканчивает тест). Аргументы программы — имена
  тестов, по умолчанию все.
- **Известная, ещё не исправленная проблема:** `TODO("причина")` в начале
  теста. Его провал выводится как `not ok K - имя # TODO` и не валит прогон;
  если тест прошёл — `ok K - имя # TODO`, и `run.sh` в итоге печатает его в
  строке «TODO tests that pass now, remove TODO» (отметку пора снять).
- **Код под тестом** собирается из своего места в дереве, без копий:
  `SRCS_<модуль>` и `CFLAGS_<модуль>` в `minix/tests/host/GNUmakefile`. Типы
  NetBSD/MINIX, которых нет в glibc (например, `bitchunk_t`), тест объявляет
  сам со ссылкой на источник. Модулю со своими шагами сборки — `<модуль>/module.mk`
  (задаёт `EXTRA_<модуль>_<вариант>` — объекты и файлы, нужные тестам, и
  `CFLAGS_<модуль>`).
- **`abi64`** — раскладки типов MINIX при 32- и 64-битных `long`/указателях
  (`docs/types-audit.md` §2.2): пробник собирается с заголовками MINIX
  (`mkinc.sh` строит дерево `machine/` из исходников, для 64 бит — LP64-прослойка),
  эталон — его 32-битная сборка. Проверяет размер всех типов сообщений (56 байт) и
  `message` (64), внешние раскладки (multiboot, диск, кольца virtio, дескрипторы);
  на m64 известные поломки — `# TODO`, их число и список — «храповик» в
  `t_abi64.c`. Рядом — `scan64.py`, полный проход clang по дереву (§2.1 там же).
- **`fdt`** — libfdt в том наборе, что линкует ядро earm, на `.dtb` эталонной
  платы (`docs/devicetree.md` §3.6); `module.mk` сам собирает хостовый `dtc` и
  `.dtb`, от сборки earm не зависит.
- **Варианты сборки** (`HOST_VARIANTS`): `m32`, `m64` (`-O2`), `m32-san`,
  `m64-san` (ASan + UBSan, `-fno-sanitize-recover=all`: любое неопределённое
  поведение — падение теста). `-m32` и `-m64` вместе ловят ошибки ширины
  типов (п. 7 модернизации).
- **Изоляция:** каждый тест выполняется в своём `fork()`; падение, сигнал или
  отчёт санитайзера валят только этот тест.
- **Случайные последовательности:** `ht_rand()`, `ht_rand_below(n)`. Зерно
  печатается в начале (`# seed N`), `HOSTTEST_SEED=N` повторяет прогон.
- **Вывод** — TAP (`ok`/`not ok`, диагностика строками `#`). `run.sh` считает
  программу прошедшей, если она завершилась с кодом 0 и `ok` (вместе с
  `not ok … # TODO`) столько, сколько в плане. Журнал — `obj/test-logs/host-<дата>.log`, итог — `.result`
  (`RESULT: PASS|FAIL`), код возврата 0/1; объектные файлы —
  `obj/host-tests/<вариант>/`.
- `selftest` проверяет сам каркас: провал проверки, `REQUIRE`, падение по
  сигналу и отчёт ASan должны давать «не прошёл» (под ASan `SIGSEGV`
  перехватывает санитайзер — код 1, а не сигнал); тест под `TODO()` — код 3
  (ожидаемый провал) или 4 (прошёл).
- Тесты внутри MINIX (ATF/kyua из NetBSD) — после libpthread (п. 8); этот
  каркас — только для хоста.

## 2. Точка отсчёта (2026-09-30)

Коммит: исходное дерево MINIX 3.4 + исправление idle (§4.1). i386, QEMU с KVM
(хост: AMD, MS-7C95), `-m 1024 -smp 1`, диск PIO (`ata_no_dma=1`).

**Результат: 100 из 101.** Упал только `isofs` — ошибка `makefs` (§4.2). После
исправления и пересборки (2026-10-01, загрузка с DMA) `isofs` проходит:
**101 из 101**.

**Первый автоматический прогон (2026-10-01):** `make test-i386`, 1 CPU, KVM, DMA —
**101 из 101, PASS**, около 24 мин вместе с загрузкой. Перед этим `TESTS=1,2,43`
три раза подряд PASS (после исправления §4.3).

Ожидаемый «шум» в журнале, тесты при этом проходят:
- test64: `anon_pagefault: out of memory`, `SIGSEGV`, coredump — тест проверяет
  нехватку памяти;
- test68: `verify_grant: grant failed: invalid flags`, `TTY: sys_safecopyfrom()
  failed` — тест проверяет отказ по неверным грантам;
- test65: `mkntfs or ntfs-3g not found, skipping test`;
- testvnd: `VFS: block driver disappeared!`, `blockdriver: bad I/O vector`,
  `VND0: data copy failed` — тест проверяет ошибки драйвера vnd.

процессам, крутящимся на других CPU) молчит ещё дольше: 2026-10-03 прогон
`TESTS=79` занял 2318 с, а полный прогон с `HANG_IDLE=1800` остановился на нём
ложным `HANG` (дамп: система жива, два «работающих» процесса теста опущены SCHED
в очередь 15). Для полного прогона на 4 CPU — `HANG_IDLE=3000 TEST_TIMEOUT=9000`.
Тест 41 молчит ~2 мин, поэтому `HANG_IDLE` меньше ~200 с не ставить и для
`TESTS=41`.

обычным ядром — около 24 мин: в **~2,5 раза медленнее**, хотя процессоров
вдвое больше. Это ожидаемая цена текущей архитектуры, а не ошибка: одна
большая блокировка ядра (BKL) и все системные процессы на BSP (§5.4). Каждый
вызов пользовательского процесса, оказавшегося на AP, — это IPI, выход AP из
`hlt` и ожидание BKL. По `dbg_cpu_events` CPU1 получил за прогон ~68,8 млн
IPI (в среднем ~18 тыс./с), CPU0 — ~11,5 млн. Добавляют простои 57
тайм-аутов диска (§5.3). Архитектуру сейчас не меняем — задача этапа
привести SMP в рабочее состояние; мелкие блокировки и размещение системных
процессов — п. 4 `docs/modernization.md`. Сравнивать время прогонов можно
только при одинаковом числе CPU.

Четыре теста нагружают разные части системы и служат метриками производительности

коды возврата `sched_yield()`/`ipc_minix_yield()`, пинг-понг двух процессов через

тиками (`CLOCK_MONOTONIC`, ~16 мс), поэтому «0.00 s» — норма. На SMP игроки могут
оказаться на разных CPU — тогда тест проходит, не задевая перестановку очереди.

SMP-ядро на 4 CPU — 2167 нс; пинг-понг < 1 тика в обоих случаях. На 4 CPU
пинг-понг напечатал «-0.00 s»: `CLOCK_MONOTONIC` в одном процессе вернул чуть
меньшее значение (меньше тика) — не исследовано, см. `handoff.md`.

## 4. Найденные ошибки

### 4.1 Зависание ядра в idle при прерывании в «тени» `sti` (исправлено 2026-09-30)

**Симптом.** Тест 43 через ~30 мин: гость простаивает (QEMU ~1% CPU), клавиатура и
консоли не реагируют, тики таймера не идут.

**Диагностика** (монитор QEMU `gdbserver`, дамп памяти ядра через `gdb`, разбор
`proc[]` по символам ядра):
- `EIP` в `halt_cpu` после `hlt`, `EFLAGS.IF = 0`, `proc_ptr = idle`;
- `at_wini` готов (`p_rts_flags = 0`, `MF_DELIVERMSG`) и стоит в очереди 7; `mfs`
  ждёт `at_wini`, VFS ждёт `mfs`, `test43` ждёт VFS;
- 8259: `IRR` = IRQ0 (таймер) ожидает, `ISR` пуст — контроллер исправен;
- на стеке ядра ниже `ESP` — кадр последнего прерывания `hwint14` (IRQ 14):
  **сохранённый `EIP` = адрес самой `hlt`**, `EFLAGS` после `CLEAR_IF` = `0x6`.

**Причина.** `halt_cpu` — это `sti; hlt; ret`. Путь «прерывание внутри ядра»
(`hwint_master`/`hwint_slave`/`apic_hwint`/`lapic_intr`) сбрасывает `IF` в
сохранённых флагах (`CLEAR_IF`) и делает `iret`, рассчитывая вернуться **за** `hlt`
(тень `sti` гарантирует это на реальном x86). Под KVM прерывание было принято
**до** `hlt`; `iret` вернул на `hlt` с `IF = 0` — процессор остановлен навсегда при
готовом процессе в очереди.

**Исправление** (`minix/kernel/arch/i386`): метка `halt_cpu_hlt` на инструкции `hlt`
(`klib.S`); макрос `SKIP_IDLE_HLT` (`sconst.h`) — если сохранённый `EIP` равен
`halt_cpu_hlt`, увеличить его на 1; вызывается перед `CLEAR_IF` во всех четырёх
путях (`mpx.S`, `apic_asm.S`; всего 83 обработчика). Проверено: тест 43 проходит
(39 с), полный прогон 100/101.

**На будущее.** Любой idle-цикл вида «разрешить прерывания; остановиться» с
возвратом из обработчика с запрещёнными прерываниями должен защищаться так же
(откат/пропуск инструкции остановки). Проверить при SMP (А5; AP используют тот же
`halt_cpu`) и повторить для `wfi` на ARM (Б1, В2) и в новых портах.

### 4.2 `makefs`: перепутаны `atime` и `mtime` в Rock Ridge `TF` (исправлено 2026-09-30)

**Симптом.** Тест `isofs`: у каталогов в ISO время модификации на 1–4 с раньше, чем
в исходном дереве; файлы совпадают.

**Причина.** `usr.sbin/makefs/cd9660/iso9660_rrip.c:cd9660node_rrip_tf` (NetBSD-8,
rev. 1.14) ставит флаги `MODIFY | ACCESS | ATTRIBUTES`, но пишет `st_atime` в слот
MODIFY и `st_mtime` в слот ACCESS. Сервер `isofs` читает поле по спецификации RRIP.
У каталога `atime` остаётся временем `mkdir`, отсюда расхождение.

**Исправление.** Порядок полей как в NetBSD trunk (rev. 1.17): `st_mtime`, затем
`st_atime`. Затрагивает и host tool `nbmakefs` (образы CD, `x86_cdimage.sh`).

### 4.3 test43: гонка с `procfs` (исправлено 2026-10-01, ошибка теста)

**Симптом.** В автоматическом прогоне `TESTS=1,2,43` тест 43 стабильно падал
(`realpath` → `ENOENT` при ожидаемом успехе), сам по себе и вручную проходил.

**Причина.** Тест через `link_1.tmp → /` обходит всю ФС, включая `/proc`, и
многократно (из разных текущих каталогов) проверяет каждый путь. Процесс,
оставшийся от теста 2, завершался во время обхода — `/proc/<pid>` исчезал между
проверками. Найдено добавленной в тест диагностикой: путь
`…/link_1.tmp/proc/./939`.

**Исправление** (`minix/tests/test43.c`): не спускаться внутрь ФС типа `procfs`
(`statvfs` → `f_fstypename`); сам `/proc` проверяется. Диагностика (путь, текущий
каталог, результат, ожидаемые ошибки) при любом расхождении оставлена.

Ложные следы, проверенные по дороге (на заметку): «система не успокоилась после
загрузки» — нет; режим TAP — нет; загрузка через `-kernel` и `snapshot=on` — нет.
Решающим было отличие в наборе тестов (43 после 2), а не в окружении.

### 4.4 SMP: окно с IF=1 в `restore_user_context_sysenter` (исправлено 2026-10-01)

**Симптом.** SMP-ядро изредка зависало при загрузке; CPU0 крутится в
`arch_spinlock_lock(&big_kernel_lock)`.

**Причина.** Возврат в пользовательский режим через `sysexit`: `popf` загружал
PSW процесса с IF=1 ещё в ядре, уже после `context_stop(KERNEL)` (BKL отпущен).
Прерывание в этом окне шло путём «прерывание в ядре» →
`context_stop_idle()` → BKL взят, и `sysexit` уносил его в пользовательский
режим. В `restore_user_context_syscall` то же окно, да ещё на пользовательском
стеке. Ошибка из оригинального MINIX.

**Исправление** (`minix/kernel/arch/i386/mpx.S`): IF сбрасывается в значении до
`popf`; прерывания включает `sti` (тень `sti` покрывает `sysexit`) или сам
`sysret`.

### 4.5 Повторный параметр ядра не заменял прежний (исправлено 2026-10-01)

**Симптом.** `KARGS=no_apic=1` при `CPUS>1` не действовал: в строке было
`no_apic=0 … no_apic=1`, выигрывал первый.

**Причина.** `mb_set_param()` (`arch/i386/pre_init.c`, `arch/earm/pre_init.c`)
при поиске существующего ключа делал лишний `p++` после конца строки и
сравнивал со сдвигом все записи, кроме первой: дубликат дописывался в конец, а
`get_value()` возвращает первое вхождение. Ошибка из оригинального MINIX.

**Исправление:** лишний `p++` убран (оба файла).

### 4.6 SMP: `hlt` без обработчика — ядро без BKL и с IF=1 (исправлено 2026-10-01)

**Симптом.** После 4.4 SMP-ядро (и в однопроцессорном режиме) продолжало
зависать: CPU0 в `hlt` получает прерывание, `context_stop_idle()` ждёт BKL,
который занят им же.

**Как найдено.** `bkl.txt`: перед зависанием два `unlock` подряд из `idle()` без
`lock` между ними — `halt_cpu()` вернулся, не пройдя ни через один обработчик
(`hlt` закончился иначе: NMI, SMI, ложное пробуждение виртуального CPU), и
оставил IF=1. Дальше ядро работает без BKL с разрешёнными прерываниями;
прерывание до следующего `hlt` берёт BKL, `idle()` засыпает, держа его, и
следующее прерывание из `hlt` блокирует CPU на себе.

**Исправление:**
- `klib.S`, `halt_cpu`: `cli` после `hlt` — в ядро никогда не возвращаемся с
  IF=1 (`SKIP_IDLE_HLT` из 4.1 теперь переводит на `cli`);
- `proc.c`, `idle()` (SMP): если после `halt_cpu()` `cpu_is_idle` ещё стоит,
  обработчика не было — `idle()` сам вызывает `context_stop_idle()` (учёт idle
  и BKL).

После 4.4–4.6: SMP-ядро в однопроцессорном режиме (`CPUS=4 KARGS=no_apic=1`) —
PASS 101/101 (два прогона), обычное ядро — PASS 101/101.

### 4.7 SMP: остановка процесса, ещё работающего на другом CPU (исправлено 2026-10-01)

**Симптом.** На 2 CPU в тесте 41: `assert "!(mp->mp_flags & (PROC_STOPPED |
VFS_CALL | UNPAUSED | EVENT_CALL))"` в PM (`do_sigprocmask`), PM падает.

**Причина.** Флаги RTS, выставленные с другого CPU (например, `RTS_SIGNALED` в
`cause_sig()`), только убирают процесс из очереди — CPU, на котором он
выполняется, узнаёт об этом при следующем входе в ядро. `smp_schedule_stop_proc()`
синхронно останавливал через IPI только процесс из очереди готовых; для такого
«уже не готового, но ещё работающего» процесса флаг ставился напрямую. PM писал
кадр сигнала (`sys_sigsend`) в контекст процесса, который продолжал работать на
другом CPU: контекст затирался, процесс делал вызовы, которых PM от
остановленного не ждёт.

**Исправление** (`minix/kernel/smp.c`): `proc_is_running_remote(p)` — процесс
текущий на своём CPU; тогда `smp_schedule_stop_proc()` и
`smp_schedule_vminhibit()` идут через синхронный IPI. Ошибка из оригинального
MINIX.

### 4.8 SMP: регистры SYSENTER/SYSCALL программировались не тем CPU (исправлено 2026-10-01)

**Симптом.** Под TCG (`ACCEL=tcg`) SMP-ядро на 2 CPU паникует при первом
`sysenter`: отказ страницы по `CR2=0x44` в `ipc_entry_sysenter`, BSP работает на
стеке ядра CPU1. Под KVM не проявлялось (системные вызовы там шли через `int`).

**Причина.** MSR `SYSENTER_CS/ESP/EIP` и `STAR` у каждого CPU свои. `tss_init()`
писала их, а в SMP её для всех CPU по очереди вызывает BSP (`tss_init_all()`):
у BSP оставались стек и точка входа последнего CPU, AP не настраивались вовсе.

**Исправление:** запись MSR вынесена в `tss_init_msrs(cpu)` (`protect.c`,
`arch_proto.h`); BSP вызывает её для себя после `tss_init_all()`, каждый AP — для
себя в `ap_finish_booting()` (`arch_smp.c`). Ошибка из оригинального MINIX.

### 4.9 SMP: `pci` без `acpi` в режиме APIC (исправлено 2026-10-01)

**Симптом.** `pci: panic: PCI: Cannot use APIC mode without ACPI!` при
`no_apic=0`.

**Причина и исправление.** `ramdisk/rc` запускал `acpi` только при параметре
`acpi=`. Теперь — и при `no_apic=0` (`minix/drivers/storage/ramdisk/rc`).

### 4.10 SMP: устаревшая проверка `RC_DELAY` в `do_runctl` (исправлено 2026-10-01)

**Симптом.** После 4.7 на 2 CPU тест 41 по-прежнему иногда роняет PM тем же
assert: `!(mp->mp_flags & (PROC_STOPPED | …))` в `do_sigprocmask`.

**Причина.** Другой путь к тому же состоянию. PM останавливает процесс P
(`sys_delay_stop`, флаг `RC_DELAY`). `do_runctl` проверяет «P не отправляет
сообщение», затем для P на другом CPU вызывает `smp_schedule_stop_proc` →
`smp_schedule_sync`, а та **отпускает BKL**, пока ждёт чужой CPU. В это окно P
входит в ядро с вызовом к PM и ждёт BKL. Получив его, CPU P сначала выполняет
запрос остановки (`context_stop` → `smp_sched_handler`: `RTS_PROC_STOP`), но
**системный вызов после этого всё равно выполняется** (`do_ipc` не смотрит на
`RTS_PROC_STOP`), и сообщение встаёт в очередь к PM, который занят этим самым
kernel call. PM получает `OK` вместо `EBUSY`, ставит `PROC_STOPPED` и затем
принимает вызов от «остановленного» процесса. На одном CPU kernel call атомарен,
и окна нет. Ошибка из оригинального MINIX.

**Исправление** (`minix/kernel/system/do_runctl.c`): после
`smp_schedule_stop_proc` проверка `RC_DELAY` повторяется. Если P уже отправляет
(`RTS_SENDING` или `MF_SC_DEFER`), то `MF_SIG_DELAY`, снять `RTS_PROC_STOP`,
вернуть `EBUSY` — как на одном CPU. PM получит `SIGSNDELAY`, когда сообщение
будет принято.

**Проверено:** четыре прогона теста 41 на 2 CPU (три `TESTS=41` и полный) —
падения PM нет, тест 41 падает только по таймерам (§5.1).

**На будущее.** Любой kernel call, который вызывает `smp_schedule_sync`, видит
после него мир, изменившийся за время без BKL; проверки, сделанные до вызова,
нужно повторять. Тот же вопрос — к `smp_schedule_vminhibit` (VM), не
разобрано.

### 4.11 SMP: AP заканчивал загрузку в таблицах загрузки, EOI уходил в память (исправлено 2026-10-02)

**Симптом.** На 2 CPU тест 41 падал: `ITIMER_VIRTUAL/PROF` не срабатывали,
`times()` давал utime = stime = 0. Тики на AP почти не шли: за полный прогон
CPU1 получил 35 тыс. тиков и 68,8 млн IPI. Ядро нарочно останавливало таймер
AP в `idle()`. Если остановку убрать, AP глох после первого же тика: вектор
240 оставался в `ISR`, `PPR 0xf0`, таймер и IPI блокировались. То же под TCG,
то есть ошибка гостя, а не KVM (AVIC на хосте выключен).

**Как найдено.** Диагностика в ядре: перед `hlt` читать `ISR` своего LAPIC,
плюс журнал событий загрузки (`dbg_boot_ev`: метка, CPU, TSC, `CR3`,
`lapic_eoi_addr`, `ISR`). AP ушёл во второй `hlt` с уже взведённым
битом 240, то есть EOI после тика не дошёл до LAPIC. Журнал показал порядок:

```
AP lapic_enable  cpu1  0 мс     cr3 = таблица загрузки   EOI = 0xfee000b0 (физ.)
AP hlt           cpu1  30 мс    cr3 = таблица загрузки
enable_paging    cpu0  31 мс    LAPIC переведён на 0xf10060b0 (вирт.)
AP timer         cpu1  51 мс    cr3 = таблица загрузки   EOI = 0xf10060b0
```

**Причина.** Предполагалось, что AP заканчивает загрузку внутри
`wait_for_APs_to_finish_booting()`, которую BSP вызывает из
`arch_enable_paging()`, когда переходит на таблицы страниц VM и виртуальный
адрес LAPIC. Но BSP отпускает BKL при каждом запуске процесса, задолго до
этого. AP успевал взять BKL, запустить LAPIC по физическому адресу и уснуть в
`hlt` с `CR3` таблиц загрузки. Затем BSP переводил `lapic_addr`/
`lapic_eoi_addr` на виртуальный адрес. Первое прерывание на AP выполняло EOI
по виртуальному адресу через таблицы загрузки, и запись уходила в обычную
память (молча портя её). Остановка таймера в `idle()` эту ошибку
маскировала: `stop_local_timer()` делает лишний `apic_eoi()` уже после
`switch_address_space_idle()`, то есть в таблицах VM, и он снимал застрявший
вектор IPI. Ошибка из оригинального MINIX.

**Исправление.**
- `smp.c`: `wait_for_BSP_paging()` — AP ждёт флага, который BSP ставит в
  `wait_for_APs_to_finish_booting()`. `arch_smp.c`, `ap_finish_booting()`:
  ждать флаг до `boot_lock`/BKL, затем `switch_address_space(VM)`, и только
  потом работать с LAPIC;
- `proc.c`, `idle()`: таймер AP в простое больше не останавливается, как и
  на BSP. Процесс на AP получает тики и процессорное время.

**Проверено:** загрузка на 2 CPU с работающим таймером AP (раньше висла на
«Started VFS»); тики на CPU0 и CPU1 идут поровну (9601 и 9596 за 164 с,
60 Гц); `TESTS=41` на 2 CPU — **PASS**.

**На будущее.** AP не должен ничего делать с устройствами по адресам, которые
BSP может перевести, пока AP живёт в чужом адресном пространстве. На ARM
(В2) тот же вопрос — GIC и таймер, переход от физических адресов к
виртуальным.

### 4.12 SMP: ошибки запуска LAPIC на AP (исправлено 2026-10-02)

Найдены по коду при разборе 4.11 и исправлены вместе с ней
(`arch/i386/apic.c`, `arch_smp.c`). Все — из оригинального MINIX.

1. **Калибровки на AP не было, на BSP она завышала частоту тиков в ~7 раз.**
   `apic_calibrate_clocks()` считала прерывания IRQ0 от PIT по статическому
   `probe_ticks`, который никто не сбрасывал. На AP цикл заканчивался сразу,
   и AP брал замеры BSP. На BSP KVM досылал накопившиеся IRQ0 пачкой:
   141 МГц вместо 1 ГГц, ~420 тиков/с при `hz 60`. Вдобавок на AP
   калибровка отпускала BKL, разрешала прерывания, вешала обработчики с
   хуками на своём стеке на IRQ0 (его обслуживает BSP, а обработчик делал
   `BKL_UNLOCK()`) и оставляла работать PIT.
   **Теперь:** каждый CPU опрашивает канал 2 PIT (порт 0x61, режим 0,
   3 раза по 10 мс, берётся кратчайший), без прерываний и без снятия BKL;
   частота LAPIC и TSC — для своего CPU. Результат: 1000 МГц на обоих CPU,
   тики 60 Гц.
2. **`LVTERR` на AP не настраивался** (вектор 0, маска): ошибки LAPIC на
   AP не доходили до обработчика. Теперь `lapic_set_error_vector()`
   вызывают и `apic_idt_init()` (BSP), и `ap_finish_booting()`.
3. **`copy_trampoline()`**: в IDT для trampoline копировалась GDT. Теперь
   копируется `idt`.
4. **INIT IPI.** `APIC_ICR_TM_LEVEL` был определён как 0 (`IS_CLEAR`), и
   INIT уходил фронтом. Deassert шёл всем CPU, включая себя
   (`DEST_ALL`), режимом Fixed с вектором 0 — это недопустимый вектор,
   ошибка в ESR на всех CPU. Теперь `TM_LEVEL` — бит 15, а deassert —
   `DM_INIT | level | deassert` адресно (как в Linux). Под TCG прежде LAPIC
   CPU1 выглядел сброшенным (`SPIV 0xff`, `LDR 0`); после исправления этого
   нет.
5. **Запись в `CCR`.** Регистр только для чтения (SDM); остановку таймера
   делает `ICR = 0`. Лишняя запись убрана из `lapic_stop_timer()` и из
   калибровки.

### 4.13 SMP: AP работал с выключенным кэшем и без `CR0.WP` (исправлено 2026-10-02)

**Симптом.** В дампах `CR0` у CPU1 был `0xe0000033` (TCG) или `0x80000033`
(KVM), у CPU0 — `0x8001003b`: на AP оставались CD = NW = 1 (кэш выключен,
как после сброса) и не было WP. На железе AP работал бы без кэша, а без WP
ядро на AP может писать в страницы пользователя, защищённые от записи.

**Причина.** Trampoline AP (`trampoline.S`) только добавлял к `CR0` биты PE
и PG. На BSP WP включает `pg_utils.c` при переходе на страничную адресацию,
а CD/NW снимает загрузчик или BIOS. Ошибка из оригинального MINIX.

**Исправление:** в trampoline при переходе в защищённый режим снимаются CD
и NW, вместе с PG ставится WP (`I386_CR0_CD`, `I386_CR0_NW` добавлены в
`vm.h`). **Проверено:** `CR0` CPU1 = `0x8001003b` под KVM и TCG;
`TESTS=41` на 2 CPU — PASS.

### 4.14 VFS: повторно открытая FIFO писала в освобождённый узел PFS (исправлено 2026-10-02)

**Симптом.** Первый полный прогон на 4 CPU: упал тест 31 (`mkfifo`).
Дочерний процесс читает «banana» из FIFO, закрывает её, открывает на
запись — `write` возвращает `EINVAL`; родитель затем читает 0 байт. При
10 запусках `TESTS=31` на 4 CPU — 4 падения; на 1 и 2 CPU не встречалось.

**Причина.** `EINVAL` возвращает PFS: узла FIFO у него нет
(`pfs_findnode() == NULL`). При последнем закрытии `put_vnode()` (VFS) шлёт
`req_putnode` в MFS и в PFS, куда отображены данные FIFO. Это блокирующие
вызовы, рабочий поток VFS в это время уступает управление. Если в это окно
другой поток открывает ту же FIFO, `advance()` (`path.c`) находит vnode и
«оживляет» его (ветка «vnode vanished»). Для MFS это верно: поиск пути снова
взял ссылку на inode. А узел PFS `put_vnode()` уже освободила, но
`v_mapfs_e` не сбрасывала. `map_vnode()` видит «уже отображено» и не
создаёт новый узел, и чтение и запись идут в несуществующий узел. На 4 CPU
закрытие в одном процессе и открытие в другом приходят в VFS почти
одновременно — окно стало попадаться. Ошибка из оригинального MINIX.

**Исправление** (`minix/servers/vfs/vnode.c`, `put_vnode()`): после
`req_putnode` отображённой ФС сбрасывать `v_mapfs_e = NONE`,
`v_mapinode_nr = 0`. Ожившая FIFO отображается в PFS заново (новый пустой
канал, как и положено после закрытия всех дескрипторов). Анонимные каналы
(`pipe()`, `v_mapfs_e == v_fs_e`) не затронуты.

**Проверено:** 10 запусков `TESTS=31` на 4 CPU — 10/10 PASS (до исправления
4 падения из 10).

### 4.15 SMP: `top` ронял ядро делением на ноль (исправлено 2026-10-02)

**Симптом.** На SMP-ядре с 4 CPU `top` от root — паника ядра; на
последовательной консоли просто тишина после команды. Найдено владельцем
вручную, воспроизведено `run-i386` (ввод конвейером: `root`, `top`), текст
паники снят с экрана VGA:

```
Divide error  cpu 0  eip=0xf043861b     (__udivmoddi4 ← __udivdi3 ← get_cpu_ticks
                                          ← do_getinfo ← kernel_call; вызвал mib)
kernel panic: Unhandled kernel exception
```

**Причина.** `top` читает `kern.cp_time`. MIB (`servers/mib/kern.c`)
запрашивает тики `sys_getcputicks()` для **каждого из `CONFIG_MAX_CPUS`**
(8) процессоров, а ядро (`do_getinfo`, `GET_CPUTICKS`) проверяет только
`cpu < CONFIG_MAX_CPUS`. `get_cpu_ticks()` делит на `tsc_per_tick[cpu]`,
а у CPU, которые не запускались (4–7 при `-smp 4`), он равен 0 (по
памяти: `64940372 64929907 64921781 64916646 0 0 0 0`). На ядре без SMP
`CONFIG_MAX_CPUS = 1`, в тестах `kern.cp_time` не читается. Ошибка из
оригинального MINIX.

**Исправление** (`arch/i386/arch_clock.c`, `arch/earm/arch_clock.c`):
для CPU без длины тика `get_cpu_ticks()` возвращает нули.

### 4.16 `<minix/bitmap.h>`: сдвиг `int`-единицы на 31 (исправлено 2026-10-02)

**Найдено** первым же тестом на хосте (§1д, `minix/tests/host/bitmap`): в
вариантах с UBSan `left shift of 1 by 31 places cannot be represented in type
'int'`. `GET_BIT`/`SET_BIT`/`UNSET_BIT` и `bit_set`/`bit_unset`/`bit_isset`
сдвигали `1` (тип `int`): для бита 31 это неопределённое поведение. Макросы
используют ядро (`p_stale_tlb`), VM (`alloc.c`, `acl.c`), DS, VFS,
`libminixfs`, `tty` и др. gcc пока генерирует «ожидаемый» код, но вправе
считать такой сдвиг невозможным. Ошибка из оригинального MINIX.

**Исправление:** `CHUNK_BIT(bit)` = `(bitchunk_t)1 << CHUNK_OFFSET(bit)` в
`*_BIT`, `1U << (n)` в `bit_*` (все пользователи `bit_*` — маски не шире
32 бит, поэтому `~(1U << n)` не теряет старших битов).

**Проверено:** `host-test` — PASS во всех вариантах; полный `hdimage`
обычный и SMP; дизассемблер ядра, модулей загрузки и `/service/*` совпадает с
собранным до исправления (77/77 в обеих сборках, `/usr/service` не
сравнивался); обе системы (1 CPU и SMP на 4 CPU) загрузились и прошли первые
36 и 31 тест, после чего прогоны остановлены — код не изменился, полный прогон
не нужен.

## 5. Открытые проблемы

### 5.1 SMP: учёт времени на AP — закрыто 2026-10-02

Причина — 4.11 (AP глох без остановки таймера в простое), сопутствующие
ошибки — 4.12. Тест 41 на 2 CPU проходит. Отдельно (не нужно для тестов):
учитывать процессорное время по TSC в `context_stop()`, а не по тикам, —
точнее и нужно для безтикового режима.

### 5.2 Калибровка таймера LAPIC завышала частоту тиков — закрыто 2026-10-02

См. 4.12, п. 1: калибровка опросом канала 2 PIT, 1000 МГц, 60 Гц.

### 5.3 SMP (APIC): тайм-ауты записи на диск `AT0-D0: timeout on command 0xca` — не воспроизводится с 2026-10-02

В прогонах на 2 CPU до §4.12 — десятки сообщений `timeout on command 0xca`
(WRITE DMA), 57 за прогон. После §4.12 (тики 60 Гц вместо ~420) — ни
одного за полный прогон. Вероятная причина: тайм-ауты, отсчитываемые в
тиках (`at_wini`, `tickdelay`), истекали в ~7 раз раньше реального времени.
Если появится снова — разбирать заново (IRQ 14 через IOAPIC на BSP).

### 5.4 SMP: межпроцессорный IPC очень медленный (тест 70)

Тест 70 (два процесса × 5 млн `lseek` к VFS) на 2 CPU шёл порядка 10–20 минут.
Не зависание: по снимкам ~190 тыс. входов в ядро в секунду, CPU0 постоянно в
`apic_send_ipi`, CPU1 будится IPI планировщика (за 328 с ~5,7 млн IPI) и
уходит в `hlt`. Причина: системные процессы (VFS, MFS, …) SCHED сажает только
на BSP (`pick_cpu`), пользовательский процесс может оказаться на AP; тогда
каждый вызов — IPI + выход из `hlt` + BKL. Это худший случай текущего SMP,
а не ошибка; вопрос к п. 4 модернизации (размещение системных процессов,
idle без `hlt` на коротких ожиданиях, мелкие блокировки). Для сравнения
нужен замер теста 70 на 1 CPU.

### 5.5 SMP: `asyn failed for message entry in rs` — не воспроизводится с 2026-10-02

Было дважды между тестами 72 и 73 на 2 CPU до §4.12 (`proc.c:1513`/`1602`,
`tab 0xffffffff` во втором). После §4.12 в полном прогоне на 2 CPU не было.
Возможная связь — та же частота тиков (тайм-ауты RS) или порча памяти EOI
из §4.11. Если появится снова — разбирать.

### 5.6 SMP: кэш на AP и `CR0.WP` — закрыто 2026-10-02, см. 4.13

### 5.7 SMP: паника `uds` в тесте 90 на 4 CPU — известная, не воспроизводится

Во втором полном прогоне на 4 CPU (2026-10-02,
`obj/test-logs/i386-smp-cpu4-20261002-060935.*`, снимок `snapshot-3669s`,
дамп `.postmortem`) после теста 89 упал сервер UNIX-сокетов:

```
minix/net/uds/io.c:285: assert "*seglen <= uds->uds_len" failed, function "uds_fetch_hdr"
стек: panic ← __assert13 ← uds_fetch_hdr ← uds_recv ← sockevent_process ← sockdriver_process ← main
```

Заголовок сегмента в приёмном буфере сокета говорит о длине больше, чем
данных в буфере. Заголовки пишет сам `uds` (`uds_store_hdr`, склейка
сегментов в `uds_send_advance`, частичный приём в `uds_recv_advance`).

**Попытки воспроизвести (все 2026-10-02, SMP-ядро, 4 CPU, KVM):** тест 90
прошёл 29 раз — в первом и третьем полных прогонах, `TESTS=90` ×5,
`TESTS=56,58,90,91` и серия `TESTS=90` ×20 (6212 с,
`obj/test-logs/i386-smp-cpu4-20261002-095646.*`; часть серии шла под
нагрузкой параллельной сборки earm на хосте). Итого 1 падение на 30 проходов,
и единственное — после тестов 1–89 в одной загрузке. На 1 и 2 CPU не
встречалось.

**Что проверено.** Путь `VMINHIBIT` (`do_vmctl`, `smp_schedule_vminhibit`,
`pt_writemap` в VM) — порчи памяти не нашлось. Окно без BKL в
`smp_schedule_sync` есть (как в §4.10), но VM меняет таблицы страниц только
после возврата из `sys_vmctl`, а копирование памяти процесса с `RTS_VMINHIBIT`
ядро ловит `assert` в `lin_lin_copy`; TLB сбрасывается через `MF_FLUSH_TLB` и
`p_stale_tlb`. Буфер `uds` — в его собственной памяти; писать в него могут
только сам `uds` и ядро по его `safecopy`, а `uds` и VM работают на BSP.
Вероятнее ошибка логики `uds` при редком порядке событий (на 4 CPU отправитель
и получатель чаще на разных CPU).

**Если появится снова.** Вернуть ловушку: после каждой отправки
(`uds_send_advance`) и каждого приёма (`uds_recv_advance`) пройти цепочку
сегментов приёмного буфера — длина каждого заголовка в пределах занятой части,
сумма длин равна `uds_len`, последний заголовок в `uds_last` — и при первом
расхождении `panic` с именем операции, `tail`/`len`/`last` и местом сбоя. Так
видна операция, испортившая буфер, а не только `recv`, который не смог его
прочитать. Ловушка проверялась на тестах 56, 58, 90, 91 — ложных срабатываний
нет; из дерева убрана после серии ×20. Ловить, скорее всего, придётся полными
прогонами на 4 CPU, а не одним тестом 90.
