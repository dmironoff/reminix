# ReMinix — тестирование: прогон, точка отсчёта, найденные ошибки

> Долгоживущий документ. Как запускать регрессионные тесты `minix/tests`, эталонные
> результаты (точка отсчёта), метрики «тяжёлых» тестов и найденные при прогонах
> ошибки. Обновляйте при изменении процедуры, после новой точки отсчёта и при
> обнаружении ошибок. Критерий «тесты прошли» — `docs/modernization.md`, раздел
> «Рабочий процесс и общие решения».

## 1. Автоматический прогон (основной способ)

```sh
make -C docker -f build.mk hdimage                       # образ (rc.d/minixtests внутри)
make -C docker -f build.mk test-i386                     # все тесты, 1 CPU
make -C docker -f build.mk test-i386 TESTS=1,2,43        # выбранные
make -C docker -f build.mk hdimage SMP=yes               # SMP-сборка (obj/i386-smp)
make -C docker -f build.mk test-i386 SMP=yes CPUS=4      # прогон на 4 CPU
make -C docker -f build.mk test-i386 SMP=yes CPUS=4 KARGS=no_apic=1  # SMP-ядро на 1 CPU
```

SMP: ядро по умолчанию грузится с `no_apic=1`, и SMP-ядро уходит в
однопроцессорный режим на 8259 (`smp_single_cpu_fallback`, BKL при этом
работает). Поэтому при `CPUS>1` `run-tests.sh` сам добавляет `no_apic=0`;
`KARGS` — дополнительные аргументы ядра (свой `no_apic=` в `KARGS` отменяет
автоматический). Настоящий SMP узнаётся по строкам `CPU N is up` в журнале.
В режиме APIC `ramdisk/rc` запускает сервис `acpi` (без него `pci` падает:
«Cannot use APIC mode without ACPI»).

Прочие переменные `test-i386` (все — в `docker/build.mk`):
- `HANG_IDLE=N` — секунды тишины на консоли до признания зависания (§1б);
- `SNAPSHOT_AT=N` — через N **реальных** секунд снять снимок работающей системы
  (как post-mortem, машина продолжает работу) в `<журнал>.snapshot/`;
- `ACCEL=tcg|kvm` — вместо автоматического выбора (KVM, если доступен). TCG
  помогает отличить ошибку гостя от эффекта KVM;
- `KARGS=tickdebug=N` — каждый CPU печатает строку раз в N своих тиков (сколько
  тиков, сколько из них не IDLE, текущий процесс). **Глушит сторож тишины**: при
  зависании дампа не будет.

Как устроено (`docker/run-tests.sh`, `etc/rc.d/minixtests`):
- QEMU 11.1 (из Docker-образа) грузит ядро и модули из
  `obj/<arch>/destdir.i386/boot/minix/.temp` напрямую (`-kernel`/`-initrd`,
  multiboot), без меню загрузчика; корневая ФС — из `minix_x86[_smp].img`,
  открытого с `snapshot=on` (образ не меняется); DMA включён; консоль на
  последовательный порт;
- командная строка ядра `testrun=1 [testlist=43,71]` включает
  `rc.d/minixtests`. Скрипт выполняется **синхронно, последним в rc**
  (`REQUIRE: LOGIN inetd local`): пока rc не закончился, init не запускает getty,
  а getty делает `revoke` консоли — вывод фонового процесса пропадал бы. Пауза
  `testdelay` (30 с) перед запуском, затем `run -T`, метки
  `REMINIX-TESTS-BEGIN/END`, 5 с на опустошение очереди TTY, `halt -p`;
- на хосте: таймаут (`TEST_TIMEOUT`, 5400 с), разбор TAP, сверка с
  `docker/tests-known-failures.i386`. Итог: **PASS / FAIL** (новые падения) /
  **HANG** / **CRASH** / **INCOMPLETE**; код возврата 0/1/3. Журнал —
  `obj/test-logs/i386[-smp]-cpuN-<дата>.log` (виден мосту, присылать не нужно).

## 1а. Ручной прогон на i386 (QEMU)

Для отладки и интерактивной работы.

```sh
make -C docker -f build.mk hdimage          # образ minix_x86.img
script -c "qemu-system-i386 -enable-kvm -m 1024 -smp 1 \
  -drive file=minix_x86.img,format=raw,if=ide \
  -serial stdio" ~/reminix-run.log          # журнал всего вывода консоли
```

- Консоль на последовательный порт (иначе журнал не сохранить):
  - пункт меню 4 «ALIX» (`console=tty00 consdev=com0`, **но с `ata_no_dma=1`** —
    диск в режиме PIO, под KVM очень медленно, см. §3);
  - **предпочтительно** — пункт 6 «Drop to boot prompt» и:
    ```
    load_mods /boot/minix_default/mod*
    multiboot /boot/minix_default/kernel rootdevname=c0d0p0 console=tty00 consdev=com0
    ```
    (то же, но с DMA).
- Вход `root` без пароля, затем `cd /usr/tests/minix-posix && ./run`. Только от root
  выполняются `isofs`, `vnd`, `rmib`, `relpol`. Один тест: `./run -t 43`.
- Alt+F1..F4 в окне QEMU перехватывает GNOME — переключать консоли через монитор
  QEMU (Ctrl+Alt+2): `sendkey alt-f2`.

## 1б. Зависание: автоматический post-mortem

Если консоль молчит `HANG_IDLE` секунд (по умолчанию 600; в TAP-режиме тест
печатает только по завершении, поэтому значение больше самого долгого теста)
или прогон дольше `TEST_TIMEOUT`, `run-tests.sh` вызывает
`docker/qemu-postmortem.py`: через монитор QEMU останавливает машину и пишет в
`obj/test-logs/<журнал>.postmortem/`:

- `monitor.txt` — `info registers`, `info lapic` и стек (`x/64xw $esp`) каждого
  CPU, `info pic`, `info irq`;
- `symbols.txt` (`nm -n -S`) и `kernel` — копия ELF ядра для `objdump -d`;
- `<символ>.bin` — память ядра: `proc`, `priv`, `__cpu_local_vars`, стеки ядра
  (`k_stacks_start`), замки, `kinfo`, `kmess`…;
- `bkl.txt` (только SMP-ядро) — владелец BKL и последние 64 захвата/освобождения
  с местом вызова и функцией уровнем выше. Пишется ядром: `BKL_LOCK/UNLOCK` идут
  через `bkl_lock()/bkl_unlock()` (`minix/kernel/smp.c`); попытка CPU взять уже
  свой BKL отмечается как `RE-LOCK`.

Разбор: адреса из стека и `EIP` — по `symbols.txt`; цепочка кадров — по `%ebp`
(ядро собрано с указателями кадра; входные заглушки обнуляют `%ebp`). Под
`cpuN` с `EIP=000fd0b1`, `CR0=0x11`, `HLT=1` — AP, которые MINIX не запускал
(стоят в SeaBIOS). `EIP` в `hlt` QEMU показывает как адрес следующей команды.

Отладочные данные ядра, которые сохраняет дамп:
- `dbg_cpu_events.bin` — для каждого CPU четыре `u32`: вызовы
  `timer_int_handler`, `context_stop_idle`, IPI планировщика, уходы в `hlt` из
  `idle()` (всегда включено, `minix/kernel/clock.c`);
- `tick_debug_*.bin` (при `tickdebug=N`), `lapic_bus_freq.bin`.

`kmess` (буфер сообщений ядра) в дамп не попадает — символ называется
`kmessages`; если ядро запаниковало до вывода на консоль, причину ищите по стеку
(`k_stacks_start.bin`: `panic` ← `inkernel_disaster` ← `exception_handler`, рядом
номер исключения, код ошибки и `EIP`/`CS`), `CR2` — в `info registers`.

## 2. Точка отсчёта (2026-09-30)

Коммит: исходное дерево MINIX 3.4 + исправление idle (§4.1). i386, QEMU с KVM
(хост: AMD, MS-7C95), `-m 1024 -smp 1`, диск PIO (`ata_no_dma=1`).

**Результат: 100 из 101.** Упал только `isofs` — ошибка `makefs` (§4.2). После
исправления и пересборки (2026-10-01, загрузка с DMA) `isofs` проходит:
**101 из 101**.

**Первый автоматический прогон (2026-10-01):** `make test-i386`, 1 CPU, KVM, DMA —
**101 из 101, PASS**, около 24 мин вместе с загрузкой. Перед этим `TESTS=1,2,43`
три раза подряд PASS (после исправления §4.3).

Ожидаемый «шум» в журнале, тесты при этом проходят:
- test64: `anon_pagefault: out of memory`, `SIGSEGV`, coredump — тест проверяет
  нехватку памяти;
- test68: `verify_grant: grant failed: invalid flags`, `TTY: sys_safecopyfrom()
  failed` — тест проверяет отказ по неверным грантам;
- test65: `mkntfs or ntfs-3g not found, skipping test`;
- testvnd: `VFS: block driver disappeared!`, `blockdriver: bad I/O vector`,
  `VND0: data copy failed` — тест проверяет ошибки драйвера vnd.

**SMP (2026-10-01, KVM):**

| Режим | Результат |
|---|---|
| обычное ядро, 1 CPU | 101/101 PASS |
| SMP-ядро, однопроцессорный режим (`CPUS=4 KARGS=no_apic=1`) | 101/101 PASS (2 прогона) |

## 3. Тяжёлые тесты и метрики

Четыре теста нагружают разные части системы и служат метриками производительности
и регрессионной защитой для этапа модернизации:

| Тест | Что нагружает | Для каких шагов важен |
|---|---|---|
| **43** (`realpath` по всей ФС на глубину 4) | IPC, VFS, MFS: миллионы `stat`/`lstat`/`chdir` | ASID (В3), `kyield`, стоимость IPC; копии параллельно — многопоточный VFS (п. 8) |
| **71** (целостность через кэш MFS, кэш VM, диск; 20 000 блоков по 4 КБ) | `libminixfs`, файловый кэш VM, `at_wini` | buddy (А3) |
| **74** (`mmap` и взаимоблокировки VM ↔ VFS ↔ FS; та же нагрузка, что 71, через `mmap`) | VM регионы, page fault, `munmap` | журнал APT (А7): синхронный UNMAP, отложенное освобождение; многопоточный VFS |
| **79** (сигналы: пинг-понг по 20 000 сигналов, 8 «работ», таймер 1 мкс) | PM, ядро (`sys_kill`, `sys_sigsend`) | сигналы на поток (п. 8) |

Ещё полезные: **90** (UNIX-сокеты, передача дескрипторов через VFS — п. 8),
**`mfs`** (SHA-1 образа от `mkfs.mfs`: ловит случайное изменение формата MFS при
аудите типов, п. 7; при намеренном изменении формата хэш обновлять в том же коммите).

Замеры (время `time ./run -t N`):

| Дата | Тест | real | user | sys | Условия |
|---|---|---|---|---|---|
| 2026-09-30 | 43 | 39,41 | 1,81 | 35,83 | i386, KVM, `-m 1024 -smp 1`, PIO |
| 2026-10-01 | 43 | 37,73 | 2,40 | 34,90 | i386, KVM, `-m 1024 -smp 1`, DMA |
| 2026-10-01 | 71 | 24,00 | 4,01 | 9,36 | то же, DMA |
| 2026-10-01 | 74 | 39,15 | 5,05 | 14,53 | то же, DMA |
| 2026-10-01 | 79 | 63,00 | 14,85 | 47,11 | то же, DMA |

Тест 43 почти не зависит от режима диска (39,4 → 37,7 с): он упирается в IPC и
VFS/MFS, а не в диск — поэтому годится как метрика стоимости IPC. Тесты 71 и 74 с
PIO шли десятки минут, с DMA — меньше минуты.

Под PIO (`ata_no_dma=1`) дисковые тесты (71, 74, `mfs`) почти всё время проводят в
ядре: `at_wini` передаёт данные через kernel call `SYS_SDEVIO`, и каждое `insw` под
KVM — выход в гипервизор. Сравнивать замеры только при одинаковом режиме диска.

## 4. Найденные ошибки

### 4.1 Зависание ядра в idle при прерывании в «тени» `sti` (исправлено 2026-09-30)

**Симптом.** Тест 43 через ~30 мин: гость простаивает (QEMU ~1% CPU), клавиатура и
консоли не реагируют, тики таймера не идут.

**Диагностика** (монитор QEMU `gdbserver`, дамп памяти ядра через `gdb`, разбор
`proc[]` по символам ядра):
- `EIP` в `halt_cpu` после `hlt`, `EFLAGS.IF = 0`, `proc_ptr = idle`;
- `at_wini` готов (`p_rts_flags = 0`, `MF_DELIVERMSG`) и стоит в очереди 7; `mfs`
  ждёт `at_wini`, VFS ждёт `mfs`, `test43` ждёт VFS;
- 8259: `IRR` = IRQ0 (таймер) ожидает, `ISR` пуст — контроллер исправен;
- на стеке ядра ниже `ESP` — кадр последнего прерывания `hwint14` (IRQ 14):
  **сохранённый `EIP` = адрес самой `hlt`**, `EFLAGS` после `CLEAR_IF` = `0x6`.

**Причина.** `halt_cpu` — это `sti; hlt; ret`. Путь «прерывание внутри ядра»
(`hwint_master`/`hwint_slave`/`apic_hwint`/`lapic_intr`) сбрасывает `IF` в
сохранённых флагах (`CLEAR_IF`) и делает `iret`, рассчитывая вернуться **за** `hlt`
(тень `sti` гарантирует это на реальном x86). Под KVM прерывание было принято
**до** `hlt`; `iret` вернул на `hlt` с `IF = 0` — процессор остановлен навсегда при
готовом процессе в очереди.

**Исправление** (`minix/kernel/arch/i386`): метка `halt_cpu_hlt` на инструкции `hlt`
(`klib.S`); макрос `SKIP_IDLE_HLT` (`sconst.h`) — если сохранённый `EIP` равен
`halt_cpu_hlt`, увеличить его на 1; вызывается перед `CLEAR_IF` во всех четырёх
путях (`mpx.S`, `apic_asm.S`; всего 83 обработчика). Проверено: тест 43 проходит
(39 с), полный прогон 100/101.

**На будущее.** Любой idle-цикл вида «разрешить прерывания; остановиться» с
возвратом из обработчика с запрещёнными прерываниями должен защищаться так же
(откат/пропуск инструкции остановки). Проверить при SMP (А5; AP используют тот же
`halt_cpu`) и повторить для `wfi` на ARM (Б1, В2) и в новых портах.

### 4.2 `makefs`: перепутаны `atime` и `mtime` в Rock Ridge `TF` (исправлено 2026-09-30)

**Симптом.** Тест `isofs`: у каталогов в ISO время модификации на 1–4 с раньше, чем
в исходном дереве; файлы совпадают.

**Причина.** `usr.sbin/makefs/cd9660/iso9660_rrip.c:cd9660node_rrip_tf` (NetBSD-8,
rev. 1.14) ставит флаги `MODIFY | ACCESS | ATTRIBUTES`, но пишет `st_atime` в слот
MODIFY и `st_mtime` в слот ACCESS. Сервер `isofs` читает поле по спецификации RRIP.
У каталога `atime` остаётся временем `mkdir`, отсюда расхождение.

**Исправление.** Порядок полей как в NetBSD trunk (rev. 1.17): `st_mtime`, затем
`st_atime`. Затрагивает и host tool `nbmakefs` (образы CD, `x86_cdimage.sh`).

### 4.3 test43: гонка с `procfs` (исправлено 2026-10-01, ошибка теста)

**Симптом.** В автоматическом прогоне `TESTS=1,2,43` тест 43 стабильно падал
(`realpath` → `ENOENT` при ожидаемом успехе), сам по себе и вручную проходил.

**Причина.** Тест через `link_1.tmp → /` обходит всю ФС, включая `/proc`, и
многократно (из разных текущих каталогов) проверяет каждый путь. Процесс,
оставшийся от теста 2, завершался во время обхода — `/proc/<pid>` исчезал между
проверками. Найдено добавленной в тест диагностикой: путь
`…/link_1.tmp/proc/./939`.

**Исправление** (`minix/tests/test43.c`): не спускаться внутрь ФС типа `procfs`
(`statvfs` → `f_fstypename`); сам `/proc` проверяется. Диагностика (путь, текущий
каталог, результат, ожидаемые ошибки) при любом расхождении оставлена.

Ложные следы, проверенные по дороге (на заметку): «система не успокоилась после
загрузки» — нет; режим TAP — нет; загрузка через `-kernel` и `snapshot=on` — нет.
Решающим было отличие в наборе тестов (43 после 2), а не в окружении.

### 4.4 SMP: окно с IF=1 в `restore_user_context_sysenter` (исправлено 2026-10-01)

**Симптом.** SMP-ядро изредка зависало при загрузке; CPU0 крутится в
`arch_spinlock_lock(&big_kernel_lock)`.

**Причина.** Возврат в пользовательский режим через `sysexit`: `popf` загружал
PSW процесса с IF=1 ещё в ядре, уже после `context_stop(KERNEL)` (BKL отпущен).
Прерывание в этом окне шло путём «прерывание в ядре» →
`context_stop_idle()` → BKL взят, и `sysexit` уносил его в пользовательский
режим. В `restore_user_context_syscall` то же окно, да ещё на пользовательском
стеке. Ошибка из оригинального MINIX.

**Исправление** (`minix/kernel/arch/i386/mpx.S`): IF сбрасывается в значении до
`popf`; прерывания включает `sti` (тень `sti` покрывает `sysexit`) или сам
`sysret`.

### 4.5 Повторный параметр ядра не заменял прежний (исправлено 2026-10-01)

**Симптом.** `KARGS=no_apic=1` при `CPUS>1` не действовал: в строке было
`no_apic=0 … no_apic=1`, выигрывал первый.

**Причина.** `mb_set_param()` (`arch/i386/pre_init.c`, `arch/earm/pre_init.c`)
при поиске существующего ключа делал лишний `p++` после конца строки и
сравнивал со сдвигом все записи, кроме первой: дубликат дописывался в конец, а
`get_value()` возвращает первое вхождение. Ошибка из оригинального MINIX.

**Исправление:** лишний `p++` убран (оба файла).

### 4.6 SMP: `hlt` без обработчика — ядро без BKL и с IF=1 (исправлено 2026-10-01)

**Симптом.** После 4.4 SMP-ядро (и в однопроцессорном режиме) продолжало
зависать: CPU0 в `hlt` получает прерывание, `context_stop_idle()` ждёт BKL,
который занят им же.

**Как найдено.** `bkl.txt`: перед зависанием два `unlock` подряд из `idle()` без
`lock` между ними — `halt_cpu()` вернулся, не пройдя ни через один обработчик
(`hlt` закончился иначе: NMI, SMI, ложное пробуждение виртуального CPU), и
оставил IF=1. Дальше ядро работает без BKL с разрешёнными прерываниями;
прерывание до следующего `hlt` берёт BKL, `idle()` засыпает, держа его, и
следующее прерывание из `hlt` блокирует CPU на себе.

**Исправление:**
- `klib.S`, `halt_cpu`: `cli` после `hlt` — в ядро никогда не возвращаемся с
  IF=1 (`SKIP_IDLE_HLT` из 4.1 теперь переводит на `cli`);
- `proc.c`, `idle()` (SMP): если после `halt_cpu()` `cpu_is_idle` ещё стоит,
  обработчика не было — `idle()` сам вызывает `context_stop_idle()` (учёт idle
  и BKL).

После 4.4–4.6: SMP-ядро в однопроцессорном режиме (`CPUS=4 KARGS=no_apic=1`) —
PASS 101/101 (два прогона), обычное ядро — PASS 101/101.

### 4.7 SMP: остановка процесса, ещё работающего на другом CPU (исправлено 2026-10-01)

**Симптом.** На 2 CPU в тесте 41: `assert "!(mp->mp_flags & (PROC_STOPPED |
VFS_CALL | UNPAUSED | EVENT_CALL))"` в PM (`do_sigprocmask`), PM падает.

**Причина.** Флаги RTS, выставленные с другого CPU (например, `RTS_SIGNALED` в
`cause_sig()`), только убирают процесс из очереди — CPU, на котором он
выполняется, узнаёт об этом при следующем входе в ядро. `smp_schedule_stop_proc()`
синхронно останавливал через IPI только процесс из очереди готовых; для такого
«уже не готового, но ещё работающего» процесса флаг ставился напрямую. PM писал
кадр сигнала (`sys_sigsend`) в контекст процесса, который продолжал работать на
другом CPU: контекст затирался, процесс делал вызовы, которых PM от
остановленного не ждёт.

**Исправление** (`minix/kernel/smp.c`): `proc_is_running_remote(p)` — процесс
текущий на своём CPU; тогда `smp_schedule_stop_proc()` и
`smp_schedule_vminhibit()` идут через синхронный IPI. Ошибка из оригинального
MINIX.

### 4.8 SMP: регистры SYSENTER/SYSCALL программировались не тем CPU (исправлено 2026-10-01)

**Симптом.** Под TCG (`ACCEL=tcg`) SMP-ядро на 2 CPU паникует при первом
`sysenter`: отказ страницы по `CR2=0x44` в `ipc_entry_sysenter`, BSP работает на
стеке ядра CPU1. Под KVM не проявлялось (системные вызовы там шли через `int`).

**Причина.** MSR `SYSENTER_CS/ESP/EIP` и `STAR` у каждого CPU свои. `tss_init()`
писала их, а в SMP её для всех CPU по очереди вызывает BSP (`tss_init_all()`):
у BSP оставались стек и точка входа последнего CPU, AP не настраивались вовсе.

**Исправление:** запись MSR вынесена в `tss_init_msrs(cpu)` (`protect.c`,
`arch_proto.h`); BSP вызывает её для себя после `tss_init_all()`, каждый AP — для
себя в `ap_finish_booting()` (`arch_smp.c`). Ошибка из оригинального MINIX.

### 4.9 SMP: `pci` без `acpi` в режиме APIC (исправлено 2026-10-01)

**Симптом.** `pci: panic: PCI: Cannot use APIC mode without ACPI!` при
`no_apic=0`.

**Причина и исправление.** `ramdisk/rc` запускал `acpi` только при параметре
`acpi=`. Теперь — и при `no_apic=0` (`minix/drivers/storage/ramdisk/rc`).

## 5. Открытые проблемы

### 5.1 SMP: локальный таймер AP и учёт процессорного времени

**Симптом.** На 2 CPU тест 41 падает: `ITIMER_VIRTUAL/PROF` не срабатывают
(подтест 4 — 0 сигналов, подтест 7 — процесс жив через 60 с), `times()` даёт
utime = stime = 0 (диагностика добавлена в `minix/tests/test41.c`).

**Что установлено.**
- Тест работает на CPU1. `tickdebug`: строк `tick cpu1` нет вообще.
- Снимок: CPU1 в `idle()` → `stop_local_timer()`; `LVTT` замаскирован. За прогон
  CPU1 получил 9 тиков, CPU0 — 10630.
- Механизм: `idle()` на AP **останавливает** локальный таймер (one-shot), каждое
  пробуждение заводит его на полный тик. Процесс, который блокируется чаще раза в
  тик (цикл с `time()`), тика на AP не видит — ему не начисляется время.
- Попытка не останавливать таймер на AP (как на BSP) **ломает загрузку**: CPU1
  после первого же тика перестаёт принимать прерывания.
  - KVM: `ISR 240` (таймер) висит, хотя обработчик отработал и сделал EOI
    (счётчики `dbg_cpu_events`: таймер 1, `context_stop_idle` 1, `hlt` 2);
    `IRR 240 241`, `PPR 0xf0` — AP глух к таймеру и IPI.
  - TCG: LAPIC CPU1 выглядит **сброшенным** (`SPIV 0xff` — APIC disabled,
    `LDR 0`), хотя `lapic_enable()` на AP выполнялся («Calibrating clock»);
    `IRR 240 241`, обработчик таймера не вызывался ни разу.
  - Вывод: инициализация/состояние LAPIC на AP неверны, а `apic_eoi()` внутри
    `stop_local_timer()` в простое это маскировал.
- Подозреваемые для разбора: калибровка таймера на AP (идёт по IRQ0, который
  обрабатывает BSP; `calib_clk_handler` читает CCR и делает `BKL_UNLOCK` на
  чужом CPU), deassert INIT IPI в `apic_send_init_ipi()` (`DEST_ALL`, режим
  доставки Fixed, вектор 0 — всем, включая себя), последовательность
  `lapic_enable()` на AP. В коде сейчас — исходное поведение MINIX
  (`proc.c`, `idle()`, комментарий со ссылкой сюда).

**Направление решения.** (1) Найти причину по LAPIC AP. (2) Независимо —
учитывать процессорное время по TSC в `context_stop()` (разность TSC при
выходе из процесса уже считается), а не по прерываниям таймера: точно, не
зависит от таймера AP, нужно для безтикового режима.

### 5.2 Калибровка таймера LAPIC завышает частоту тиков примерно в 7 раз

В режиме APIC ядро меряет частоту шины LAPIC за 5 прерываний IRQ0 от PIT
(`apic_calibrate_clocks`, ≈83 мс) и получает ~140 МГц; в QEMU/KVM таймер LAPIC —
1 ГГц. Тики идут в ~7 раз чаще (`hz 60`: 15300 тиков гостя за 41 с реального
времени). Тем же интервалом меряется частота TSC. Вероятно, KVM досылает
накопившиеся IRQ0 пачкой. Исправление: калибровка опросом канала 2 PIT
(порт 0x61), без прерываний и на каждом CPU своим LAPIC. В однопроцессорном
режиме (тики от PIT) время верное.
